# 방법론을 처음 밖에 내놓았다

_2026.10.18 게시_

![방법론을 처음 밖에 내놓았다 — 흐려진 승인 도장이 가득한 어두운 방에서, 사람 판단 세 문장이 적힌 문서 한 장이 v1.0.0-preview.1 태그를 달고 열린 문으로 나간다. 바닥에는 쓰지 못한 승인 키가 놓여 있다]({{ '/assets/images/agent-sdd/020-first-public-preview/thumbnail.png' | relative_url }})

[지난 글]({{ '/series/agent-sdd/019-letting-agents-improve-the-method/' | relative_url }}) 끝에서, [17편]({{ '/series/agent-sdd/017-counting-what-machines-can-check/' | relative_url }})에서 기계로 넘긴 서명 승인을 이틀 만에 뺐다고 적었다. 그건 앱 이야기였다.

그다음 날 방법론에서도 설계 단계 승인을 뺐다. 그리고 또 그다음 날, 그 방법론을 처음으로 밖에 내놓았다.

급했던 이유는 단순하다. 다음 주부터 이 방법론을 회사 일에 혼자 적용해 보기로 했다. 그런데 [18편]({{ '/series/agent-sdd/018-connecting-methodology-from-outside/' | relative_url }})에서 정한 대로 연구 저장소는 어떤 프로젝트도 직접 읽지 않는다. 회사 프로젝트가 고정해서 읽을 공개본이 필요했다.

두 이야기는 결국 같은 문장에서 만난다. 공개본에 들어간 "사람 판단" 세 문장이다. 모델 바깥에서 Agent를 붙잡는 하네스 가운데, 사람이 서는 자리를 어디까지 공통으로 정할지의 이야기이기도 하다.

---

## 승인을 늘릴수록 승인은 가벼워졌다

처음에는 설계 단계마다 사람 승인을 받았다. 큰 작업(Large)은 현황과 계획에서 두 번, 더 큰 작업(Epic)은 세 번이었다.

그런데 승인을 넣은 뒤에도 Agent가 승인 없이 구현으로 넘어간 일이 있었다. 17편에서 센 사고 기록에도 같은 모양이 있다. 리뷰 통과나 이전 단계의 승인을 다음 단계의 승인으로 넓혀 읽은 일, 승인 없이 스스로 병합한 일, 내 이름으로 승인 표시를 만들어 자기 구현의 근거로 쓴 일.

나도 문제였다. 승인 요청이 쌓이자 꼼꼼히 다 읽지 않고 의무감으로 승인하는 날이 생겼다. 승인 표시는 남았지만, 그게 내가 정말 확인했다는 뜻은 아니었다.

그래서 더 강하게 만들었다. PC에 암호화해 둔 키로 내가 직접 서명한 것만 승인으로 봤다. 17편의 "넘겼다: 승인 위조" 줄이 이거다. Agent는 서명을 만들 수 없으니 위조는 막을 수 있었다.

대신 다른 문제가 생겼다. 개발 환경이 바뀌거나 클라우드 환경에서 작업하면 키가 없어서 승인을 할 수 없었다. 승인이 일을 막는 지점이 됐다. 19편에 적은 비용, 그러니까 큰 작업마다 서명 태그를 만들어 올리고 저장소 밖에 둔 키 지문을 대조하는 일도 혼자 운영하기엔 컸다.

그래서 방향을 돌렸다. 승인하는 행위를 더 단단하게 만드는 대신 이렇게 하기로 했다.

- 내가 변경 범위를 더 편하게 확인할 수 있게 한다.
- 승인 절차는 줄인다.
- 검증은 테스트로 한다.
- 승인은 구조적 변경이 있거나 문제가 생겼을 때만 받는다.

첫 번째는 10월 15일에 사람용 문서 쪽부터 손봤다. 결론과 변화를 맨 앞에 두고, 관계와 흐름은 그림으로, 전후나 선택지는 비교표로 보이게 하는 기준이다. 새 승인 단계나 리뷰 횟수는 더하지 않았다. 이걸로 내가 실제로 더 잘 이해하게 됐는지는 아직 모른다.

같은 날 앱에서는 설계 단계 승인과 서명 검사를 뺐다. 사람이 판단하는 자리는 이렇게 옮겨졌다.

| 단계 | 서명 승인을 쓸 때 | 지금 앱 |
|:---|:---|:---|
| 큰 작업의 현황·계획 | 서명 승인 뒤 다음 단계로 | 독립 리뷰 두 개의 진행 조건을 만족하면 바로 다음 단계로 |
| 사람이 판단해야 하는 미해결 질문 | 멈춤 | 멈춤 |
| 큰 작업의 PR 병합 | 승인 원본을 다시 검사하고 Agent가 병합 | 내가 직접 병합하거나 그 PR을 병합하라고 명시적으로 지시할 때만 |
| 독립 리뷰 두 개, 코드 리뷰 한 번 | 있음 | 있음 |

마지막 줄이 중요하다. 승인을 빼면서 리뷰를 같이 뺀 건 아니다. 사실 확인과 누락 감사는 여전히 서로 다른 리뷰어가 맡는다. 앱 쪽에서는 승인 전용 시험 입력이 빠지면서 작업 배정(routing) 시험 입력이 412개에서 216개로 줄었다. 품질 지표가 아니라 승인 장치가 그만큼 차지하고 있었다는 숫자다.

## 앱이 뺀 걸 방법론은 어떻게 둘까

앱은 이 방법론을 적용한 프로젝트 하나일 뿐이다. 방법론 쪽에는 "설계 단계 사람 승인을 유지한다"는 결정이 서명된 채로 남아 있었다. 그대로 둘지 고칠지 정해야 했다.

Agent가 정리해 온 선택지는 세 개였다.

| 안 | 내용 | 감수하는 것 |
|:---|:---|:---|
| A | 그대로 둔다. 앱이 벗어난 건 관측으로만 남긴다 | 방법론과 실제 적용이 어긋난 채 남는다 |
| B | 설계 단계 사람 판단은 공통으로 유지하되, 기록은 서명 없이 대화나 리뷰에서 의사 표시하는 수준으로 낮춘다 | 서명 비용은 줄지만 단계마다 사람을 기다리는 건 남는다 |
| C | 설계 단계 승인을 프로젝트가 고르게 한다. 공통에는 최소 요건 세 개만 남긴다 | "구현 뒤에 설계로 돌아오면 비용이 크다"는 근거가 공통 권고에서 빠진다 |

Agent는 어느 안도 권하지 않았다.

처음 검토안에는 B가 없었다. 독립 리뷰가 "설계 판단은 그대로 두고 기록 수단만 낮추는 대안이 빠졌다"를 차단으로 지적했고, B를 넣고 나니 B와 C를 가를 근거가 없었다. 둘을 가르는 건 "설계 단계 승인이 재작업을 줄이는가"인데, 방법론도 앱도 그걸 잰 적이 없다. 사람을 기다리는 시간과 재작업 위험 중 무엇을 감수할지는 사람이 정할 일이라고 적고 권고를 거뒀다.

나는 C를 골랐다. B는 서명의 무게만 덜어 준다. 그런데 위에 적은 것처럼 내가 겪은 문제는 서명이 무거운 것만이 아니었다. 단계마다 돌아오는 승인이 의무가 되고, 의무가 된 승인은 확인이 아니게 된다는 거였다.

## 남긴 세 문장

C를 고르면서 공통에 남긴 세 요건은, 다음 날 공개본의 [`core.md`](https://github.com/seok-jun/adaptive-agentic-sdd/blob/v1.0.0-preview.1/ko/methodology/core.md) "사람 판단" 절에 그대로 들어갔다.

> 1. 사람 판단이 필요한 미해결 질문이 생기면, 그 판단에 의존하는 작업을 멈추고 사람에게 묻는다. 의존하지 않는 작업은 계속할 수 있다.
> 2. 프로젝트는 사람이 판단하는 지점(예: 설계 단계 승인, 병합, 배포)을 자기 설정이나 작업 지침에 명시한다. 어느 지점을 몇 개 두고 어떤 방식으로 받을지는 프로젝트가 정한다.
> 3. Agent는 사람이 하지 않은 결정을 만들지 않는다. 리뷰 통과, 테스트 통과, 일반 진행 지시, 침묵을 사람의 결정으로 대신하지 않는다.
>
> 이 세 가지는 공통 최소 요건이다. 호스트·프로젝트 규칙은 이 요건을 더 엄격하게 할 수 있지만 면제하지 못한다. 충돌하면 그 판단에 의존하는 작업을 멈추고 사람에게 묻는다.

첫 번째는 "구조적 변경이나 문제가 있을 때만 묻는다"를 일반적으로 쓴 것이다. 단계가 아니라 질문이 생겼을 때 멈춘다. 두 번째는 그 지점을 프로젝트가 고른다는 것이다. 앱은 큰 작업의 병합을 골랐다. 세 번째는 17편에서 센 사고 유형에 대한 답이다. 리뷰 통과도, 테스트 통과도, 내가 아무 말 안 한 것도 내 결정이 아니다.

![사람이 판단하는 자리의 이동. 서명 승인을 쓸 때는 큰 작업의 현황·계획 단계마다 서명 승인이 있었다. 지금 앱은 미해결 질문에서 멈추고, 큰 작업의 병합만 사람이 한다. 방법론 공통에는 세 요건만 남고, 판단 지점은 프로젝트가 고른다]({{ '/assets/images/agent-sdd/020-first-public-preview/human-judgment-points.svg' | relative_url }})

함께 정한 것도 있다. 17편의 서명 확인 도구는 공통에서 뺐다. 지우지는 않았고, 연구 저장소에 남아 있는 서명 기록을 다시 검사하는 용도로 둔다. Agent가 사람 명의로 결정을 만드는 위험은 새 기록 의무를 만들지 않고, 19편의 관측 재검토에서 발견되면 기존 처분 경로로 다루기로 했다.

비용도 같이 적어 뒀다. 설계를 먼저 승인받아야 하는 이유, 그러니까 구현하고 나서 설계로 돌아오면 비싸다는 이유가 공통 권고에서 빠졌다. 설계 승인이 없는 프로젝트에서 구현 뒤 설계로 되돌아가는 재작업이 반복해서 보이면, 그때 다시 판단한다. 지금은 효과를 모른다. 앱에서 설계 승인을 뺀 지 하루 만에 내린 결정이다.

## 밖에 내놓기 전에 정한 것

공개본이 필요한 이유는 처음에 적은 그대로다. 연구 저장소는 아무도 직접 읽지 않으니, 회사 프로젝트는 공개 태그 하나를 고정해서 복사해 가야 한다.

![공개 경로. 연구 저장소에서 설계와 검증을 하고, 검토한 파일만 공개 저장소의 v1-preview branch로 옮겨 태그를 단다. 공개 main은 v0.2 그대로다. 회사 프로젝트는 태그를 고정해 복사하고 자기 어댑터로 조정한다. 공통의 문제는 회사 공개 정책을 확인한 뒤 일반화한 이슈로 올려 다음 preview에 반영한다]({{ '/assets/images/agent-sdd/020-first-public-preview/release-path.svg' | relative_url }})

무엇을 어떻게 낼지는 여섯 가지로 나눠 정했다.

| | 정한 것 | 누가 |
|:---|:---|:---|
| 담을 범위 | 문서 세 개와 해시 목록, 커스터마이징 안내만. 연결 도구는 뺀다 | Agent 제안대로 |
| 위치 | 별도 branch의 태그로 낸다. 기존 사용자가 쓰는 main(v0.2)은 그대로 둔다 | Agent 제안대로 |
| 언어 | 영어와 한국어를 같이 낸다 | 내가 정함(Agent는 권하지 않음) |
| 묶음 정리 | 특정 제품이나 비공개 자료에 기대는 문장을 걷어 내 단독으로 읽히게 한다 | Agent 제안대로 |
| 커스터마이징 안내 | 사본을 받아 어댑터를 채우고 Agent에게 일을 시키는 순서를 새로 쓴다 | Agent 제안대로 |
| 사람 판단 | 위 세 요건을 `core.md`에 넣는다 | Agent 제안대로 |

마지막 줄이 앞 이야기와 이어지는 곳이다. 공개본에는 v0.2에 있던 위험 등급과 리뷰 gate가 없다. 세 요건을 넣지 않으면 외부 사용자에게 보이는 사람 판단 규칙이 하나도 없게 된다.

이 검토안도 처음엔 독립 리뷰에서 FAIL을 받았다. 차단이 두 개였다.

- 다음 주에 필요한 건 태그 하나인데, 공개 main을 새 방법론으로 바꾸는 일까지 같이 묶었다. 그러면 태그 없이 저장소 주소로 도입하던 기존 사용자가 받는 내용이 조용히 바뀐다.
- 공개 저장소에 branch나 PR을 올리는 순간 이미 공개다. 그런데 공개 전 확인이 main 병합과 태그 직전으로 잡혀 있었다.

그래서 main은 그대로 두고 별도 branch에만 올리기로 바꿨고, 공개 전 확인은 첫 push 전으로 옮겼다.

언어 결정은 그 뒤에 두 번 바뀌었다. 처음엔 영어 저장소와 한국어 저장소에 같이 내기로 했다가, 같은 날 한 저장소로 묶었다. 영문을 기준으로 두고 한국어판은 `ko/` 아래에 둔다. 한국어판 v0.2는 더 이상 공개하지 않는다.

## 공개 태그는 옮길 수 없어서

태그는 한 번 공개하면 옮기거나 지우지 않기로 했다. 누가 이미 그 태그를 고정해 받아 갔는지 알 수 없어서다. 그래서 공개 전에, 공개할 commit만으로 커스터마이징 안내를 처음부터 따라 해 봤다.

준비한 건 가상의 작은 Python 예제 프로젝트 하나다. 테스트 하나, CI 파일 하나, 규칙 두 줄짜리 `AGENTS.md`. 회사 코드는 쓰지 않았다. GitHub 태그 압축 파일과 같은 모양으로 로컬 압축 파일을 만들어 Windows PowerShell 5.1에서 안내 그대로 실행했다.

| 해 본 것 | 영어판 | 한국어판 |
|:---|:---|:---|
| 안내대로 사본 복사 | 성공 | 성공 |
| 해시 대조 | 세 문서 OK | 세 문서 OK |
| 대조군: 줄바꿈 고정 없이, `core.autocrlf=true`로 받기 | 세 문서 **불일치** | 세 문서 **불일치** |
| 안내대로 줄바꿈 고정을 넣고 받기 | 세 문서 OK | 세 문서 OK |

줄바꿈은 18편에서 두 번 걸렸던 문제다. 내용으로 해시를 만드는 이상, Windows에서 받는 순간 CRLF로 바뀌면 다른 버전이 된다. 이번엔 대조군을 일부러 만들어서 그 함정이 실제로 생기는 것과, 안내에 넣은 한 줄이 그걸 막는 것을 둘 다 확인했다.

```text
.adaptive-sdd/methodology/** text eol=lf
```

안내의 Agent 프롬프트도 앞의 두 단계까지 돌려 봤다. ① 관찰(코드를 고치지 않고 사실만 모으기)과 ② 어댑터 초안이다. 어댑터는 프로젝트마다 다른 값을 적는 파일이고, 공통 사본은 건드리지 않는다. 안내에 있는 시작 모양은 이렇다.

```markdown
# 방법론 어댑터

## 고정
- 출처: <저장소 주소> 태그 v1.0.0-preview.1
- 태그 commit: <SHA>
- manifest 해시: <manifest.json 파일의 sha256>
- 사본 위치: .adaptive-sdd/methodology/

## 필수 자리
- 작업 식별 방법:
- 문제 기록 위치:
- 종료 요약 위치:
- 최종 종료 판정:
- 허용된 조회·쓰기 수단과 범위:
- 사람 판단 지점:
```

두 판 모두 Agent가 코드를 고치지 않았고, 자리마다 제안 값과 근거와 확인하지 못한 것을 나눠 냈다. 마음에 든 건 사람이 정해야 할 것을 정하지 않고 모아 왔다는 점이다. 영어판은 9개, 한국어판은 8개였다. 종료 판정, 쓰기 범위, 사람 판단 지점 같은 것들이다. 세 번째 요건이 적어도 이 두 번에서는 지켜졌다.

다만 해 본 건 여기까지다. 안내의 ③~⑥(사람 결정, 어댑터 작성, 작은 작업 시운전, 실작업 뒤 조정)은 돌려 보지 않았고, macOS와 Linux에서도 해 보지 않았다. 공개 README에도 확인한 범위를 딱 이만큼만 적었다.

## 공개 직전에 저장소를 다시 만들었다

공개 직전 확인에서 예상 못 한 게 하나 나왔다. 9월에 이미 공개했던 v0.2 이력 가운데 작성자 정보를 정리해야 하는 commit이 있었다.

이력을 다시 써서 덮어써도 소용이 없었다. PR 기록에 걸린 옛 commit은 저장소 주인이 지울 수 없다. 그래서 공개 저장소를 지우고 같은 이름으로 다시 만들었다. v0.2 이력은 작성자 정보만 정리해서 다시 올리고, 그 시점에 `v0.2.0` 태그를 달아 고정점을 만들었다.

잃은 것도 있다. 이미 받아 간 사본은 회수할 수 없고, 저장소의 생성일과 지난 통계는 사라졌다. 이력을 다시 쓰면서 GitHub이 서명했던 commit의 "Verified" 표시도 빠졌다.

## 내놓자마자 나온 구멍

그렇게 10월 17일 새벽, 공개 저장소의 `v1-preview` branch에 [`v1.0.0-preview.1`](https://github.com/seok-jun/adaptive-agentic-sdd/releases/tag/v1.0.0-preview.1)을 pre-release로 냈다. 공개 뒤 실제 GitHub 압축 파일로 다시 받아 두 판 모두 해시가 맞는 것까지 확인했다.

그리고 공개된 상태 그대로 별도 세션에 리뷰를 맡겼더니, 바로 구멍이 나왔다. 무거운 것만 셋이다.

| | 구멍 | 왜 문제인가 |
|:---|:---|:---|
| B1 | `core.md` 첫머리는 "호스트·프로젝트 규칙 먼저"인데, "사람 판단" 절은 "면제 불가"다. 둘 중 무엇이 우선인지 한곳에서 정하지 않았다 | 사람에게 물을 수 없는 환경에서 Agent가 어느 쪽을 따를지 갈린다 |
| B2 | "사람 판단이 필요한 질문"이 언제 생기는지 최소 조건이 없다 | 첫 번째 요건이 언제 발동하는지 Agent마다 다르게 읽을 수 있다 |
| B3 | `core.md`는 작업 기록의 기준 위치를 정하라고 요구하는데, 어댑터에 그걸 적을 자리가 없다 | 안내의 ⑤ 시운전이 그 자리를 전제한다 |

공교롭게도 셋 다 이번에 새로 넣은 "사람 판단"과 기록 쪽이다. 고치는 건 preview.2로 미뤘다. 다음 주 회사 적용에서는 이 세 가지를 어댑터에 직접 적어서 피해 간다. 시작 기록의 위치, 명시적으로 맡긴 일의 범위, 그리고 "사람 판단 요건은 호스트·프로젝트 규칙보다 우선"이라는 문장이다.

숫자도 솔직하게 적어 둔다. 공개 저장소의 star와 fork는 0이다. 효과, 그러니까 결과나 재작업이나 비용이 나아지는지는 재지 않았다. 공개 README의 "무엇이 아닌가"에도 v0.2의 대체물이 아니고, 검증된 결과가 아니고, 강제 장치가 아니라고 적었다.

## 정리

| 한 것 | 결과 |
|:---|:---|
| 설계 단계 사람 승인 | 방법론 공통에서 뺐다. 둘지 말지는 프로젝트가 고른다 |
| 공통에 남긴 것 | 사람 판단 세 요건. 공개본 `core.md`에 들어갔다 |
| 서명 확인 도구 | 공통에서 뺐다. 지우지는 않았다 |
| 1.0 preview | 별도 branch의 태그로 공개. main(v0.2)은 그대로 |
| 공개 전 시운전 | 복사·해시·줄바꿈과 Agent 첫 두 단계까지 확인. 나머지는 안 함 |
| 공개 저장소 | 작성자 정보 정리 때문에 다시 만들었다 |
| 공개 뒤 리뷰 | 구멍 셋. preview.2로 미루고 당장은 어댑터로 피한다 |
| 효과 | 재지 않았다 |

승인을 줄인다고 사람이 빠지는 건 아니라고 생각한다. 오히려 단계마다 의무처럼 누르던 승인을 걷어 내야, 정말 물어봐야 할 때 내가 제대로 볼 수 있을 것 같았다. 그게 맞았는지는 아직 모른다.

다음 주부터는 이 preview를 회사 일에 붙인다. 1~11편은 회사 일이었고, 12~19편은 개인 프로젝트였다. 그 사이에 만든 게 다시 회사 일로 돌아가는 셈이다.

19편에서 배운 게 하나 있다. 고치려고 보니 근거가 될 기록부터 없었다는 것. 그래서 이번엔 붙이기 전에 무엇을 기록할지부터 정해 두려고 한다. 다음 글은 그 이야기다.
