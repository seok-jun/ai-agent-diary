# 켄트 백 글의 근거 공개 범위와 해석 구분

## AS-IS

- 5절의 Mission 설명이 6절 이후 비교에서 이어지지 않는다.
- 7절의 비공개 PR·결정문·CI 링크는 독자가 확인할 수 없으며, 공개 근거 메모에도 내부 문서 경로와 비공개 커밋 식별자가 남아 있다.
- 구조 정리를 독립된 동작이라고 표현해, 새 기능 요청을 계기로 하는 정리가 백의 초록 선에 못 미치는 것처럼 읽힐 수 있다.

## TO-BE

- 6절에서 작업 완료와 사용자 변화·Mission 달성의 차이를 받아주고, 이후 논의는 정리 작업 선택에 집중한다고 밝힌다.
- 비공개 링크를 제거하고 실제 diff에서 확인한 변경 전후 호출과 모듈 배치를 짧게 공개한다. 원본 전체와 실행 로그를 공개한 것으로 표현하지 않는다.
- 공식 강연 전문의 기능 사이 정리 맥락을 근거로, 사례를 초록 선에 부합하는 작업으로 설명한다.
- 기능 요청이 없는 영역의 정리 선택은 필자가 확장한 질문으로 본문·도식·맺음말에서 구분한다.
- 본문과 공개 근거 메모에서 불필요한 내부 문서 경로·비공개 커밋 해시·접근 불가능한 링크를 제거한다.

## 제약 조건

- 공개 v0.2와 실제 프로젝트 운영 사례의 시점을 구분한다.
- 기존 검증 기록과 이번에 실행한 검사를 구분한다. 기능 연동 전체의 완료나 장기 변경 비용의 감소를 주장하지 않는다.
- 코드 발췌는 실제 diff와 일치해야 하며 설명용 생략 범위를 표시한다.
- 저장소 공개 설정과 Git 이력은 변경하지 않는다. 현재 파일에서 제거해도 과거 커밋에 남는다는 한계를 사용자에게 알린다.

## 검증 기준

- 공식 강연과 필자의 확장 질문이 구분되고, 변경 전후 코드가 실제 diff와 일치한다.
- 공개 대상 현재 파일에 비공개 링크·내부 문서 경로·해시가 남지 않는다.
- SVG 렌더링, Markdown 코드 블록, 내부 경로, `git diff --check`, Pages 빌드 및 배포 본문을 확인한다.

## 후속 검토

- 정리 후보의 발굴 책임·우선순위와 배포 후 Mission 확인 방식은 글의 질문으로 남기며 방법론 규칙으로 확정하지 않는다.
