# 켄트 백 글 7절 관점 수정

## AS-IS

- 6절과 7절이 분석·위험 재평가의 장점을 반복하고, 가상 알림 사례로 같은 결론에 도달한다.
- 운영 경험을 뒷받침하는 구체적인 작업 근거가 없으며, 독립적인 구조 정리를 언제 선택하는지에 관한 긴장이 약하다.

## TO-BE

- 6절은 공개 v0.2가 이미 다루는 부분을 비교표와 짧은 설명으로 압축한다.
- 7절은 정리를 독립된 작업으로 실행할 수 있다는 사실과, 어떤 정리를 언제 선택할지 결정하는 일을 구분한다.
- 사용자가 지정한 `my-honey-chat`의 PR #54를 실제 사례로 쓴다. 기존 파서 발견 → 공통 모듈 추출 결정 → 별도 선행 PR → 코드 및 검증 기록을 연결한다.
- 이 사례의 정리 계기도 새 연동 요청이었다는 점을 밝히고, 새 기능이 없는 영역의 구조 비용을 어떤 조건에서 작업으로 올려야 하는지 분석한다.
- 기능 변경이 없는 안정된 영역을 반드시 청소해야 한다고 단정하지 않는다. 반복 수정·회귀 검증의 어려움 등 관찰된 비용과 정리의 비용·위험을 비교한다.
- 도식과 맺음말은 작업 선택과 선택된 작업의 실행 절차 사이의 차이를 보여준다.

## 제약 조건

- 기존 강연 출처와 공개 v0.2 비교 기준을 유지한다.
- 공개 워크플로의 무관한 리팩터링 제한을 독립적인 정리 작업의 금지로 오독하지 않는다.
- 사례는 공개 v0.2 배포 전 프로젝트의 실제 운영 기록이다. 동일한 규칙 버전을 준수했다는 증거로 취급하지 않는다.
- 비공개 저장소는 사용자가 실제 사례의 출처로 지정했다. 본문에는 해당 구조 변경과 검증에 필요한 내용만 요약하고 원시 대화·비밀·무관한 제품 정보를 옮기지 않는다.
- PR 본문의 테스트 개수와 실제 테스트 파일의 개수가 다르므로 개수를 근거 없이 인용하지 않는다. CI의 성공과 검증 범위를 구분한다.
- 변경 비용 감소의 장기 실측이나 새 공급사의 실제 모델 응답 품질을 입증했다고 쓰지 않는다.
- 새 점검 항목이나 AI 운영 규칙을 저장소에 도입하지 않는다.

## 검증 기준

- 선택과 실행의 차이, 사례의 근거와 한계가 본문·도식에서 일치한다.
- SVG XML 파싱, 실제 렌더링의 글자·화살표·겹침, 내부 링크와 이미지 경로를 확인한다.
- `git diff --check` 및 GitHub Pages의 Jekyll 빌드를 확인하고 공개 본문의 변경을 확인한다.
