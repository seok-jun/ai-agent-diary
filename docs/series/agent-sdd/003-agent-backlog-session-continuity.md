> 이 글은 이전 글에서 다룬 “Agent에게 바로 개발시키지 않고, 단계별 산출물을 만든 뒤 구현한다”는 방식의 연장선이다.
> 이번에는 그중에서도 **백로그를 왜 단순 TODO가 아니라 Agent의 세션 연속성을 유지하는 장치로 사용했는지**를 정리한다.

> 미리 짚어두면, 여기서 말하는 "백로그"는 스크럼의 Product Backlog나 Sprint Backlog(우선순위가 매겨진 할 일 대기열)와는 다른 의미다. 이 글에서는 이미 시작한 하나의 작업 단위(BL-xx)에 대한 **진행 상태 + 판단 기록 + 확인 기준**을 가리키는 말로 쓴다. 그럼에도 "백로그"라는 이름을 쓰는 이유는, 원래 "아직 안 한 일"을 적던 파일이 실무를 거치며 판단 기록까지 흡수한 것이지, 처음부터 다른 개념을 설계한 게 아니기 때문이다.

## 0. 결론부터

AI Agent로 실무 개발을 하다 보면 가장 먼저 체감하는 문제가 있다.

**Agent의 기억은 생각보다 믿을 수 없다는 것**이다.

대화가 길어지면 앞에서 합의한 내용을 놓치고, 세션이 바뀌면 이전 판단의 맥락이 사라진다.
같은 요구사항을 보고도 Agent마다 다른 전제를 세우고, 이전에 결정한 구현 방향과 다른 코드를 작성하기도 한다.

그래서 나는 Agent 작업에서 백로그를 단순한 체크리스트로 보지 않는다.

백로그는 다음 역할을 한다.

```text
- 작업을 쪼개는 문서
- 진행 상태를 기록하는 문서
- 다음 세션이 이어받을 수 있는 문서
- 다른 Agent가 같은 맥락을 공유하는 문서
- 사람이 최종 판단할 수 있는 기준 문서
```

즉, 백로그는 단순 TODO가 아니라 **Agent의 세션 밖에 존재하는 실행 상태**다.

## 1. Agent에게만 맥락을 맡기면 생기는 문제

처음에는 Agent에게 요구사항을 설명하고 바로 개발을 시켰다.

간단한 작업에서는 꽤 잘 됐다.
하지만 실무 코드에서는 금방 한계가 보였다.

특히 다음 문제가 자주 발생했다.

```text
- 앞에서 합의한 조건을 뒤에서 잊는다
- 기존 코드의 예외 처리를 놓친다
- 영향 범위를 과소평가한다
- 요구사항 밖의 리팩토링을 한다
- 테스트해야 할 케이스를 일부 누락한다
- 세션이 바뀌면 이전 판단을 다시 설명해야 한다
```

문제는 Agent가 멍청해서라기보다, 작업 방식 자체가 불안정했기 때문이다.

실무 개발은 단순히 코드를 생성하는 일이 아니다.

기존 코드의 맥락, 업무 규칙, 예외 케이스, API 계약, DB 영향, 테스트 범위, 운영 리스크까지 함께 봐야 한다.
그런데 이 모든 것을 대화창 안의 컨텍스트에만 의존하면, 세션이 길어질수록 작업 품질이 흔들린다.

그래서 생각을 바꿨다.

> Agent의 기억을 믿는 대신, Agent가 참고할 수밖에 없는 외부 상태를 만들자.

그 역할을 백로그가 하게 됐다.

## 2. SDD의 Tasks와 실무 백로그

SDD, 즉 Spec-Driven Development 흐름에서는 보통 다음과 같은 단계를 둔다.

```text
Spec → Plan → Tasks → Implement
```

요구사항을 먼저 명세하고, 구현 계획을 세운 뒤, 실행 가능한 작업 목록으로 쪼개고, 그다음 구현한다.

여기서 `Tasks`는 일반적으로 구현할 작업을 작게 나누는 단계다.

예를 들면 다음과 같다.

```text
- API 요청 파라미터 추가
- Service 로직 수정
- Mapper 쿼리 변경
- 응답 DTO 필드 추가
- 테스트 케이스 작성
```

처음에는 나도 이 정도로 생각했다.

하지만 Agent로 실무 개발을 해보니, 백로그는 단순한 작업 목록 이상의 의미를 갖게 됐다.

내가 사용하는 백로그는 다음 목적을 가진다.

```text
- Agent가 어디까지 작업했는지 기록한다
- 어떤 판단을 했는지 남긴다
- 아직 결정되지 않은 내용을 분리한다
- 다음 세션에서 이어서 작업할 수 있게 한다
- 구현 Agent와 리뷰 Agent가 같은 기준을 보게 한다
```

즉, SDD에서의 Tasks가 “실행할 작업 목록”에 가깝다면, 내가 실무에서 사용하는 백로그는 **작업 목록 + 판단 기록 + 진행 상태 + 세션 복구 지점**에 가깝다.

> 참고로 GitHub의 spec-kit도 `tasks.md`라는 이름으로 비슷한 단계를 둔다. 다만 spec-kit의 tasks.md는 `plan.md`를 실행 가능한 작업 목록으로 한 번에 변환해서 구현 단계에 넘기는 산출물에 가깝고, 완료·보류·제외 같은 판단을 계속 갱신하며 세션 간 상태를 이어주는 용도로 설계된 것 같지는 않다. (spec-kit은 지금도 계속 버전이 바뀌고 있어서, 최신 버전에서 이 부분이 달라졌을 수 있다 — 정확한 최신 동작은 직접 써보고 확인이 필요하다.)

## 3. 백로그는 Agent의 외부 기억장치다

AI Agent는 컨텍스트를 가지고 작업하지만, 그 컨텍스트는 영구적이지 않다.

대화가 길어지면 흐려지고, 세션이 끊기면 사라지고, Agent를 바꾸면 다시 설명해야 한다.

그래서 나는 중요한 상태를 대화창 안에 두지 않으려고 한다.
대신 repo 안의 문서로 빼둔다.

예를 들면 이런 식이다.

```text
/specs/feature-name/
  01-requirements.md
  02-impact-analysis.md
  03-implementation-plan.md
  04-backlog.md
  05-test-plan.md
  06-review-notes.md
```

이 중에서 `04-backlog.md`는 단순히 “할 일 목록”이 아니다.

작업의 현재 상태를 표현하는 문서다.

```md
# Backlog

## 진행 상태

- [x] 기존 API 요청 흐름 분석
- [x] 관련 Mapper 쿼리 확인
- [ ] Service 분기 로직 수정
- [ ] null/empty/0 케이스 테스트 추가
- [ ] 리뷰용 변경 요약 작성

## 결정된 사항

- 기존 API 응답 구조는 유지한다.
- 신규 필드는 optional로 추가한다.
- 기존 검색 조건의 기본 동작은 변경하지 않는다.

## 보류된 사항

- 관리자 화면 노출 여부는 별도 요구사항 확인 필요.
- 배치 로직 반영 여부는 현재 작업 범위에서 제외한다.

## 주의할 점

- Mapper 쿼리 변경 시 기존 검색 결과 건수에 영향이 없어야 한다.
- null과 empty string을 동일하게 처리하면 안 된다.
- 프론트에서 0을 유효한 값으로 전달할 수 있다.
```

이런 백로그가 있으면 세션이 바뀌어도 작업을 이어가기 쉽다.

Agent에게 이렇게 말할 수 있다.

```text
/specs/feature-name/04-backlog.md를 기준으로 아직 완료되지 않은 작업만 진행해.
결정된 사항은 변경하지 말고, 보류된 사항은 구현하지 마.
작업 후 완료한 항목과 추가로 발견한 리스크를 백로그에 반영해.
```

이렇게 하면 Agent는 이전 대화에 의존하지 않고, 문서화된 상태를 기준으로 작업한다.

## 4. 세션 연속성은 생각보다 중요하다

세션 연속성의 중요성은 작업이 하루를 넘기거나, 중간에 다른 업무가 끼어들 때 바로 드러난다.
회의를 다녀오거나, 급한 운영 이슈를 처리하거나, 다음 날 이어서 작업하는 경우가 실무에서는 흔하다.
이때 대화창만 믿고 있으면 “어디까지 했더라”부터 다시 복구해야 한다.

### 실제로 겪은 일

이건 가정이 아니라 실제로 있었던 일이다.

한 번은 구현 도중에 컴퓨터가 갑자기 다운됐다. 세션은 그대로 날아갔고, 다시 켜서 새 세션을 열어야 했다.

보통이라면 이런 상황에서 “어디까지 했더라”를 기억에 의존해서 다시 더듬어야 한다. 그런데 백로그 파일에 진행 상태가 그대로 남아 있었다. 새 세션에 그 파일을 읽히는 것만으로, 중단된 지점부터 큰 문제 없이 다시 시작할 수 있었다.

이 경험 이후로 백로그는 나에게 “있으면 좋은 문서”에서 “반드시 있어야 하는 문서”로 바뀌었다. 세션이 죽어도 상태는 죽지 않는다는 걸 직접 확인한 것이기 때문이다.

반대로 백로그가 있으면 이렇게 이어갈 수 있다.

```text
어제 작업하던 feature-name의 백로그를 읽고,
미완료 항목 중 Service 분기 로직 수정부터 진행해.
기존 결정 사항은 유지하고, 새로 발견한 리스크만 review-notes에 추가해.
```

이 방식은 사람에게도 좋다.

나중에 다시 봤을 때 “내가 왜 이렇게 수정했지?”를 덜 겪게 된다.
Agent가 작성한 코드라도, 그 코드가 어떤 판단 위에서 나왔는지 추적할 수 있다.

## 5. 멀티 Agent 작업에서도 백로그가 기준점이 된다

Agent를 여러 개 쓰면 더 문제가 커진다.

예를 들어 이런 식으로 작업을 나눌 수 있다.

```text
Agent A: 영향 범위 분석
Agent B: 테스트 케이스 설계
Agent C: 구현
Agent D: 리뷰
```

보기에는 좋아 보인다.
하지만 공통 기준 없이 병렬로 돌리면 이렇게 되기 쉽다.

Agent A는 Service만 바꾸면 된다고 판단하는데,
Agent C는 Controller까지 손대고,
Agent B는 Repository 테스트만 설계하고,
Agent D는 요구사항을 다르게 해석해서 리뷰할 수 있다.

이러면 멀티 Agent가 생산성을 올리는 게 아니라, 컨텍스트를 분열시킬 위험이 있다.

> (참고로 나는 아직 이 구조를 worktree 기반으로 실제 병렬 실행까지 돌려본 적은 없다. 여기서 짚는 문제는 구조상 예상되는 리스크이고, 그래서 병렬화 전에 백로그 같은 공통 기준을 먼저 잡아두려는 것이다.)

그래서 멀티 Agent 작업에서도 백로그가 필요하다.

```text
Requirements
   ↓
Impact Analysis
   ↓
Implementation Plan
   ↓
Backlog
   ↓
Implementation
   ↓
Review
```

각 Agent는 자신이 판단한 내용을 백로그나 관련 산출물에 반영하고, 다음 Agent는 그 산출물을 기준으로 작업한다.

중요한 것은 “여러 Agent를 동시에 돌리는 것”이 아니다.

중요한 것은 **각 Agent가 같은 상태를 보고 작업하게 만드는 것**이다.

## 6. 백로그에 반드시 들어가야 하는 내용

내가 실무에서 써보니 백로그에는 단순 작업 목록만 있으면 부족했다.

최소한 다음 항목이 있어야 했다.

```text
1. 완료된 작업
2. 남은 작업
3. 결정된 사항
4. 보류된 사항
5. 작업 범위에서 제외한 사항
6. 주의해야 할 예외 케이스
7. 테스트해야 할 항목
8. 리뷰 시 확인할 항목
```

앞에서는 최소 형태의 백로그를 보여줬다면, 실무에서는 다음처럼 확장해서 쓸 수 있다.

```md
# Backlog

## 1. 완료된 작업

- [x] 기존 조회 API 흐름 확인
- [x] 관련 Service 메서드 확인
- [x] Mapper 쿼리 영향 범위 확인

## 2. 남은 작업

- [ ] 신규 조건 분기 추가
- [ ] 응답 DTO 필드 추가
- [ ] 기존 테스트 보강
- [ ] 리뷰용 변경 요약 작성

## 3. 결정된 사항

- 기존 요청 파라미터는 변경하지 않는다.
- 신규 조건은 optional로 처리한다.
- 기존 사용자 화면의 응답 구조는 깨지지 않아야 한다.

## 4. 보류된 사항

- 관리자 화면 반영은 별도 작업으로 분리한다.
- 배치 로직 반영 여부는 추가 확인 후 진행한다.

## 5. 제외 범위

- DB 스키마 변경은 하지 않는다.
- 기존 공통 유틸 리팩토링은 하지 않는다.
- 화면 디자인 변경은 하지 않는다.

## 6. 주의할 예외 케이스

- null
- empty string
- 0
- 중복 데이터
- 권한 없는 사용자
- 기존 조건과 신규 조건이 동시에 들어온 경우

## 7. 테스트 항목

- 기존 조건만 사용한 조회
- 신규 조건만 사용한 조회
- 기존 조건 + 신규 조건 조합 조회
- 조건이 없는 경우
- 권한이 없는 사용자의 요청
- 결과가 없는 경우

## 8. 리뷰 체크포인트

- 요구사항 밖의 변경이 있는가?
- 기존 API 계약을 깨지 않았는가?
- Mapper 쿼리 변경으로 기존 결과가 달라지지 않는가?
- null/empty/0 처리가 명확한가?
- 테스트가 정상/예외/회귀 케이스를 포함하는가?
```

이렇게 작성하면 Agent가 작업을 이어가기 훨씬 쉬워진다.

또한 사람 입장에서도 리뷰 기준이 명확해진다.

### 다만, 아직 고민 중인 부분

현재 내가 사용하는 백로그는 개발을 진행하면서 이것저것 테스트해보며 항목이 계속 늘어났고, 그 결과 백로그 하나가 떠안는 책임이 비대해지는 경향이 있다.

상태·판단만 남기던 문서에 예외 케이스, 테스트 항목, 리뷰 체크포인트까지 얹다 보니 파일 하나가 점점 무거워진다. 아직은 이 8개 항목을 한 파일에 그대로 담고 있지만, 이 책임을 어떻게 분산할지는 추후 고민 중이다.

## 7. 백로그 업데이트도 작업의 일부다

중요한 점은 백로그를 처음에만 작성하면 안 된다는 것이다.

Agent가 작업을 진행하면 백로그도 같이 업데이트해야 한다.

나는 Agent에게 작업 후 이런 지시를 자주 준다.

```text
구현이 끝나면 다음 내용을 갱신해.

1. 완료한 백로그 항목 체크
2. 새로 발견한 영향 범위 추가
3. 보류해야 할 항목 추가
4. 리뷰어가 확인해야 할 내용 정리
5. 테스트하지 못한 항목 명시
```

이렇게 하면 백로그가 살아 있는 문서가 된다.

반대로 백로그를 처음에만 만들고 방치하면, 실제 코드와 문서가 어긋나기 시작한다.
그러면 Agent는 오래된 문서를 기준으로 잘못된 작업을 하게 된다.

백로그는 작업 전 문서가 아니라 **작업 중 계속 갱신되는 상태 문서**여야 한다.

## 8. 백로그가 있으면 리뷰 품질도 좋아진다

리뷰 Agent를 따로 둘 때도 백로그는 유용하다.

리뷰 Agent에게 전체 코드를 막연히 보라고 하면 리뷰가 산만해진다.

대신 백로그와 구현 계획을 기준으로 리뷰하게 하면 훨씬 낫다.

```text
다음 문서를 기준으로 리뷰해.

- 01-requirements.md
- 03-implementation-plan.md
- 04-backlog.md
- 05-test-plan.md

확인할 것:
1. 요구사항을 벗어난 변경이 있는지
2. 백로그의 완료 항목이 실제 코드에 반영됐는지
3. 보류된 사항을 구현해버린 것은 없는지
4. 테스트 계획에서 누락된 케이스가 있는지
5. 기존 API 계약을 깨는 변경이 있는지
```

이렇게 하면 리뷰 Agent도 “좋아 보인다” 수준의 리뷰가 아니라, 명시된 기준에 따라 검토한다.

특히 실무에서는 이 부분이 중요하다.

AI가 만든 코드는 얼핏 보면 그럴듯하다.
하지만 실무에서 중요한 것은 그럴듯함이 아니라, 기존 시스템과의 정합성이다.

백로그는 그 정합성을 확인하기 위한 기준점이 된다.

## 9. 정리하면: 백로그는 영속 컨텍스트다

백로그는 Agent 작업에서 세션 밖에 존재하는 실행 상태이며, 다음 세션과 다음 Agent가 동일한 맥락을 이어받기 위한 영속 컨텍스트다.

대화창 안의 기억은 휘발되지만, repo 안의 백로그는 남는다. 그래서 Agent 개발에서는 “잘 프롬프트하는 법”만큼이나 “어떤 상태를 파일로 남길 것인가”가 중요하다.

## 10. 마무리

AI Agent는 코드를 빠르게 만든다.

하지만 실무에서 필요한 것은 빠른 생성물 하나가 아니라, 그 변경이 어떤 맥락과 판단 위에서 나왔는지 설명 가능한 상태다.

나는 그 역할을 백로그가 해준다고 본다.

결국 이 방식은 Agent에게 모든 걸 기억하라고 요구하는 대신, 기억해야 할 걸 파일로 남기는 것뿐이다. 다음 세션도, 다음 Agent도 그 파일을 기준으로 시작한다.

지금 내가 쓰는 방법은 이거다.
