# AI한테 일을 시킬 때, 다 똑같이 다루면 안 되더라

_2026.06.25 게시_

![AI한테 일을 시킬 때, 다 똑같이 다루면 안 되더라]({{ '/assets/images/agent-sdd/001-ai-task-grading/thumbnail.png' | relative_url }})

AI 코딩 도구를 처음 실무에 들였을 때는 바이브 코딩하듯 그냥 대화로 개발했다. "이거 해줘", "저기 고쳐줘" 하는 식으로. 빠른 것 같았는데 한계가 금방 드러났다. 맥락이 유지되지 않아 같은 설명을 반복하게 되고, 한 군데 고치면 다른 데가 틀어져서 수정이 끝없이 반복됐다.

방법을 찾다가 SDD(Spec-Driven Development)를 알게 됐다. 코드보다 명세를 먼저 쓰고, 영향 범위를 분석하고, 테스트 기준을 잡은 다음 구현에 들어가는 방식이다. 이 일련의 단계를 글에서는 'Phase'라고 부르겠다. 대화식 개발에서 겪던 맥락 유실과 반복 수정 문제는 확실히 잡혔다.

그런데 이번엔 반대 문제가 생겼다. 오타 하나 고치는 데도 md 파일을 만들어 명세를 쓰고 있으니, 이건 이거대로 비효율이었다. 가벼운 수정에까지 전체 프로세스를 씌우는 건 과했다.

어느 쪽이든 비용은 따랐다. 오버프로세싱은 시간 낭비로 끝나지만, 언더프로세싱은 운영 사고로 번진다. 비용의 성격이 다를 뿐이다. 그래서 내린 결론은 단순했다. **작업마다 프로세스의 무게를 다르게 가져가야 한다.** 그게 작업을 등급으로 나누게 된 계기다.

## 작업을 다섯 등급으로 나눴다

기준은 규모와 리스크, 두 축이다. 등급마다 적용 강도를 다르게 가져간다. 제휴사 작업의 하위 작업들을 등급에 매핑하면 이렇게 된다.

| 구분        | 예시                                                 | 권장 방식                                          |
| ----------- | ---------------------------------------------------- | -------------------------------------------------- |
| **Trivial** | 오타 수정, 문구 변경, 로그 한 줄 추가                | 짧은 지시 + diff 확인                              |
| **Small**   | 단일 파일 수정, 단순 validation 추가, 컬럼 표시 추가 | 수정 대상 파일 + 수정 금지 영역 + 테스트 케이스    |
| **Medium**  | SQL, DTO, Service, 화면 중 2개 이상 변경             | 작업지시서 + 영향 범위 분석 + 테스트 기준          |
| **Large**   | DB 변경, 외부 API 연동, 큐/배치, 여러 모듈 영향      | 전체 Phase 적용 + 별도 리뷰 세션 + 운영 체크리스트 |
| **Epic**    | 도메인 구조 변경, 신규 기능군, 다수 시스템 연동      | 작업 분할 + 병렬 에이전트 + 단계별 승인            |

제휴사 작업으로 보면 — 팝업 안내 문구 수정은 Trivial, 화면에 할인율 한 줄 표시하는 건 Small, 할인율 계산 로직과 DTO·화면을 같이 손대는 건 Medium, 제휴사 API 연동과 DB 컬럼 변경이 들어가면 Large였다. 같은 "할인 정보 작업"이라는 이름 안에 등급이 다른 일들이 섞여 있었던 거다.

등급을 나누는 진짜 이유는 **만들어야 할 산출물이 달라지기 때문**이다.

| 구분    | 최소 산출물                                                    |
| ------- | -------------------------------------------------------------- |
| Trivial | 변경 이유, diff 확인                                           |
| Small   | 수정 파일, 수정 금지 영역, 간단 테스트 기준                    |
| Medium  | 작업지시서, 영향 범위 분석, 테스트 케이스, 리뷰 체크리스트     |
| Large   | 전체 명세, DB/API 체크리스트, 운영 반영 계획, rollback 기준    |
| Epic    | 상위 설계서, 하위 작업지시서, 병렬 작업 계획, 통합 테스트 계획 |

Trivial에 전체 작업지시서를 강제하면 그게 바로 오버프로세싱이다. 반대로 Large를 짧은 지시 한 줄로 던지면 운영 사고로 돌아온다. 전체 프로세스는 Medium 이상을 기준으로 두고, 그 아래는 필요한 항목만 축약해서 적용한다.

## 분류를 사람 직관에 맡기지 않는다

여기서 한 가지 더. 규모 판단을 작업자 감에만 맡기면 과소평가가 반복된다. "별거 아닌 줄 알았는데"가 사고의 시작점이다.

그래서 **자동 격상 트리거**를 두는 게 안전하다. 내가 Small이라고 봤어도, 다음 조건에 걸리면 등급을 강제로 올린다.

- 외부 API 호출이 바뀐다 → 자동으로 Medium 이상
- DB 스키마(DDL)를 건드린다 → 자동으로 Large
- 큐/배치 로직이 바뀐다 → 자동으로 Large
- 정산·주문·금액에 닿는다 → 자동으로 Large

제휴사 작업에서 "할인율 표시"가 Small에서 끝나지 않았던 이유가 정확히 이거다. 외부 API와 금액 계산이 엮이는 순간, 그건 더 이상 Small이 아니다. 사람이 판단하기 전에 규칙이 먼저 거른다.

## Epic은 그냥 쪼갠다

도메인 구조 변경처럼 규모가 큰 Epic은 전체 Phase를 한 번에 적용하는 게 아니라, **Phase를 적용할 수 있는 단위로 쪼개는 것**이 먼저다. 상위 설계 문서로 목표 상태와 영향 범위를 정의하고, 그걸 여러 개의 Large 또는 Medium 작업지시서로 분해한 다음, 각각에 프로세스를 적용한다. 통합 테스트 계획은 따로 세운다. 하위 작업이 다 통과해도 합칠 때 깨지는 지점이 반드시 있기 때문이다.

## 결국

AI 개발 방법론은 아직 정답이 정해진 분야가 아니다. 바이브 코딩, SDD, spec-kit, 멀티 에이전트까지 매달 새로운 방식이 쏟아진다. 그래서 누가 정해준 걸 그대로 따르기보다, 일단 가져다 써보고 내 환경에 안 맞는 부분을 깎아내면서 내 규칙으로 만들어가는 과정이 필요하다.

이 등급 분류도 그렇게 나온 내 나름의 룰이다. SDD를 그대로 적용하니 가벼운 작업엔 과했고, 안 쓰자니 맥락이 무너졌다. 그 사이에서 내 작업 패턴에 맞는 선을 그은 결과다. 정답이라기보단 지금의 내 답에 가깝고, 더 써보면 또 바뀔 거다.

그리고 솔직히, 쏟아지는 방법론들 사이에서 이렇게 자기만의 룰을 세워가는 게 요즘 개발에서 제일 재밌는 부분이기도 하다.
