## 1. 에이전트가 같은 실수를 반복하면 무엇을 해야 할까?

AI 코딩 에이전트를 쓰다 보면 같은 문제가 되풀이되는 때가 있다.

분명히 지난 작업에서 잘못된 구현을 짚었고, 왜 문제인지도 설명했다. 그런데 다음 작업에서 비슷한 코드가 또 나온다.

이럴 때 가장 쉬운 대응은 `AGENTS.md`나 `CLAUDE.md`에 규칙을 추가하는 것이다.

- "이런 방식으로 구현하지 마세요."
- "반드시 이 절차를 지키세요."
- "이 문제는 전에도 있었으니 주의하세요."

처음에는 괜찮은 대응처럼 보인다. 하지만 이렇게 계속 막다 보면 규칙만 늘어난다.

규칙이 늘어날수록 에이전트가 더 안정적으로 동작할까? 아니면 지켜야 할 지침만 복잡해질까?

최근 AI 코딩 에이전트 관련 발표들을 보다가 이 고민과 이어지는 흐름을 발견했다. 에이전트에게 올바른 행동을 더 많이 설명하기보다, 잘못된 행동을 찾아내거나 구조적으로 막는 환경을 만드는 데 힘을 쏟는다는 점이다.

그중에서도 기존 코드의 구조는 물론 주석까지 다시 봐야 한다는 주장이 기억에 남았다.

## 2. 코드 생성보다 생성된 코드를 믿을 수 있느냐가 문제다

2026년 11월 11일, AI Engineer CODE에서 Lauren Tan(@poteto)이 [All Code Is Slop (Except Mine)](https://ai.engineer/code/2026/talks/lauren-tan)이라는 제목으로 발표했다.

Grok Bot을 개발하는 Lauren은 지난 한 달 동안 PR 약 3,000개를 프로덕션에 반영했다고 소개했다.

처음에는 그 숫자가 눈에 들어왔다. 하지만 발표를 따라가 보면 PR 개수는 핵심이 아니었다. 그렇게 많은 변경을 처리하면서 코드 품질을 어떻게 유지하느냐가 본론이었다.

예전에는 개발자가 코드를 쓰고 다른 개발자가 리뷰했다. 코드를 쓰는 속도가 사람의 한계에 묶여 있었으니 리뷰도 비슷한 속도로 따라갈 수 있었다.

에이전트가 여러 작업을 동시에 하기 시작하면 사정이 달라진다. 코드는 빠르게 늘어나는데, 사람이 코드를 검토할 수 있는 시간은 그만큼 늘지 않는다. 결국 코드 생성보다 검증과 신뢰 확보가 병목이 된다.

Lauren은 이 문제를 풀려면 에이전트가 일하는 환경에 투자해야 한다고 말한다. 발표에 나온 역피라미드가 그 우선순위를 보여 준다.

![Lauren Tan이 발표에서 보여 준 역피라미드. 위에서부터 codebase, static analysis, verification, prose, human review 순서로 놓여 있다]({{ '/assets/images/standalone/2026-11-18-trusting-ai-coding-agents/trust-pyramid.jpg' | relative_url }})

*발표 화면. 출처: [AI Engineer CODE 2026 — All Code Is Slop (Except Mine)](https://ai.engineer/code/2026/talks/lauren-tan)*

| 순서 | 계층 | 포함하는 것 |
| --- | --- | --- |
| 1 | 코드베이스 | API 설계, 아키텍처, 리팩터링 |
| 2 | 정적 분석 | 린트, 타입, 컴파일러, 테스트, CI |
| 3 | 검증 | 런타임 검증, 형식 검증 |
| 4 | 산문 | 규칙, Skills, `AGENTS.md` |
| 5 | 사람의 리뷰 | 기계적으로 판단하기 어려운 영역 |

에이전트에게 직접 전달하는 지침보다 코드베이스와 검증 장치가 앞에 놓여 있다.

그렇다고 산문 지침이나 사람의 리뷰가 필요 없다는 뜻은 아니다. 가능하면 잘못된 선택 자체를 어렵게 만들고, 그다음에는 기계가 잡아내게 하고, 그걸로도 안 되는 영역에 사람과 모델의 판단을 쓰자는 쪽에 가깝다.

발표에서는 Electron의 메인 프로세스와 렌더러 프로세스 사이에 잘못된 의존성이 생기는 문제를 예로 들었다. "잘못된 모듈을 참조하지 마세요"라는 지침을 쓰는 대신, 디렉터리 구조를 분명하게 나누고 의존성 분석과 린트 규칙으로 금지된 참조를 잡아내게 했다.

이렇게 해 두면 에이전트가 지침을 기억했는지, 제대로 해석했는지에 기대지 않아도 된다.

여기서 하나 더 생각해 볼 점이 있다. 에이전트에게 가장 큰 영향을 주는 입력 가운데 하나가 바로 기존 코드베이스라는 사실이다.

## 3. 잘못된 코드는 다음 에이전트의 모범 사례가 될 수 있다

발표에서 가장 기억에 남은 부분은 주석 이야기였다.

Lauren은 Cursor에서 겪은 사례를 소개했다. VS Code의 명령형 구조와 React의 선언형 구조가 부딪히는 아키텍처 문제가 있었는데, 에이전트들이 이를 `setTimeout`, `requestAnimationFrame` 같은 타이머로 임시로 때우기 시작했다고 한다.

타이머를 썼다는 것만이 문제가 아니었다. 에이전트가 이런 우회 코드를 쓰면서, 왜 이 방식이 필요한지 설명하는 주석까지 같이 남겼다.

결국 근본적인 아키텍처 문제는 그대로인 채 타이머를 쓰는 구현만 늘어났고, 앱 성능까지 나빠졌다.

여기서 주석은 문제를 찾게 돕기보다 기존의 우회 방식을 정당화하는 역할을 했다.

![아키텍처 충돌을 타이머로 우회하고 주석으로 정당화하면, 그 코드가 다음 작업의 입력이 되어 같은 우회가 반복되는 순환]({{ '/assets/images/standalone/2026-11-18-trusting-ai-coding-agents/workaround-spread.svg' | relative_url }})

이런 코드가 있다고 해 보자.

```js
// 상태 동기화가 늦어지는 문제가 있어
// 안정성을 위해 100ms 후 화면을 다시 갱신한다.
setTimeout(() => refreshView(), 100);
```

사람이 이 코드를 보면 왜 상태 동기화가 늦어지는지, 타이머가 정말 필요한지 의심할 수도 있다.

하지만 에이전트는 새 기능을 구현할 때 기존 코드베이스의 패턴을 참고한다. 이 주석을 믿을 만한 설계 근거로 받아들이면 비슷한 상황에서 같은 방식을 쓸 가능성이 있다.

물론 에이전트가 항상 그렇게 행동하는 것은 아니다. 다만 기존 코드와 주석이 입력 문맥에 반복해서 들어가면서 잘못된 패턴을 퍼뜨릴 위험이 있다는 점은 생각해 볼 만하다.

모델이 잘못된 코드를 학습해서 내부 지식이 바뀐다는 뜻은 아니다. 기존 코드베이스가 다음 작업의 입력이 되고, 그 입력이 다음 코드 생성에 영향을 준다는 뜻이다.

Lauren은 이 일을 겪은 뒤 Grok Bot에서는 주석의 약 99%를 금지하기로 했다고 설명한다. 주석은 금방 낡은 정보가 되고, 에이전트가 근본적인 해결을 피하는 핑계로 쓰기 쉬우며, 무엇보다 주석으로는 규칙을 강제할 수 없다는 이유였다.

대신 잘못된 사용을 잡아내는 린트 규칙과, 근본 원인을 고치도록 안내하는 오류 메시지를 쓴다고 한다.

중요한 건 99%라는 숫자가 아닐 것이다. 기술 부채가 코드뿐 아니라 그 코드를 정당화하는 설명을 통해서도 퍼질 수 있다는 점이다.

## 4. 그렇다면 주석을 없애고 코드를 서술형으로 쓰면 될까?

발표를 보다가 자연스럽게 다른 궁금증이 생겼다.

주석이 에이전트의 판단을 잘못된 쪽으로 끌고 갈 수 있다면, 주석을 최대한 줄이고 코드가 모든 의도를 설명하게 만드는 편이 더 좋을까?

좋은 코드는 스스로 설명할 수 있어야 한다는 말은 예전부터 있었다. 의미 있는 변수명과 함수명을 쓰고, 복잡한 로직은 적절히 나누고, 불필요한 주석을 줄이는 방식이다.

하지만 모든 코드를 자연어처럼 풀어 쓰는 것도 문제가 될 수 있다.

주문 처리 로직을 이렇게 썼다고 해 보자.

```js
await validateOrder();
await checkCustomer();
await verifyStock();
await calculateDiscount();
await preparePayment();
await executePayment();
await finalizeOrder();
```

얼핏 보면 무슨 일을 하는지 쉽게 읽힌다. 그런데 실제로는 여러 질문이 남는다.

- 각 함수는 어떤 상태를 바꾸는가?
- 트랜잭션의 경계는 어디인가?
- 중간에 실패하면 어떻게 복구하는가?
- 함수끼리 공유하는 상태는 없는가?

함수 이름을 풀어 썼다고 해서 코드의 동작과 설계가 분명해지지는 않는다. 오히려 내부 구현을 이해하려고 여러 파일과 함수를 계속 따라가야 한다면 복잡도만 올라간다. 사람에게도 문제지만 에이전트에게도 비슷한 부담이 될 수 있다.

그래서 주석을 없애느냐, 코드를 자연어처럼 쓰느냐 가운데 하나를 고를 문제는 아니라고 생각한다. 중요한 건 어떤 정보를 어디에 적느냐다.

결제 웹훅을 처리할 때 같은 이벤트가 여러 번 들어오는 상황을 생각해 보자.

```js
// 동일한 결제 이벤트가 여러 번 전달될 수 있으므로
// 중복 결제가 발생하지 않도록 주의한다.
await processPayment(event);
```

주석에 담긴 의도는 맞다. 하지만 실제로 중복 처리를 막는지는 알 수 없다.

이렇게 책임을 나눠 볼 수 있다.

```js
// 결제 제공자는 동일한 eventId를 재전송할 수 있다.
// 근거: 결제 제공자 Webhook 계약
await paymentProcessor.processIdempotently(event);
```

여기서 `processIdempotently`라는 이름은 구현이 지켜야 할 계약을 드러낸다. 주석은 코드만 봐서는 알기 어려운 외부 제약을 설명한다. 그리고 실제 멱등성은 데이터베이스의 유일성 제약, 트랜잭션 처리, 중복·동시 요청 테스트로 확인해야 한다.

함수 이름만으로 멱등성이 보장되지 않고, 주석이 있다고 보장되지도 않는다.

| 수단 | 맡는 일 |
| --- | --- |
| 코드 | 동작과 책임을 표현한다 |
| 주석 | 코드에 드러나지 않는 이유와 외부 제약을 설명한다 |
| 검증 장치 | 그 계약이 지켜지는지 확인한다 |

이렇게 역할을 나누는 편이 더 낫지 않을까.

특히 외부 시스템과의 계약이나 직관과 어긋나는 비즈니스 규칙처럼 코드만 봐서는 이유를 알기 어려운 곳에서는 주석이 여전히 쓸모가 있다.

반대로 지금 구현이 잘못된 이유를 변명하는 주석이라면 이야기가 다르다. 임시 우회가 필요하다면 왜 필요한지 적는 데서 끝내지 말고, 해결할 이슈와 제거 조건을 추적할 수 있어야 한다. 가능하면 그 우회 코드가 퍼지지 않게 막는 검사도 필요하다.

결국 주석의 양을 줄이는 것보다, 그 주석이 기존 구현을 정당화하는 수단인지 검증 가능한 설계 판단을 보완하는 정보인지 구분하는 일이 중요하다.

## 5. 검증에 토큰을 더 쓴다는 것

발표에는 눈길이 가는 이야기가 하나 더 나온다.

Lauren은 Cindy Sridharan(@copyconstruct)이 하루 토큰 사용량의 약 70%를 검증에 쓴다고 한 이야기를 소개했다. 그리고 본인도 토큰 대부분을 검증에 쓴다고 했다.

여기서 70%는 업계 평균도 아니고 Lauren 본인의 정확한 비율도 아니다. 몇몇 개발자의 경험을 모든 개발 환경의 표준으로 받아들일 수는 없다.

그래도 이 접근은 토큰 최적화를 보는 눈을 바꿔 준다.

지금까지는 에이전트가 쓰는 토큰을 줄이는 데 관심이 많았다. 컨텍스트를 압축하고, 캐시를 쓰고, 불필요한 도구 호출을 줄이고, 작업에 맞는 모델을 고르는 식이다. 이런 최적화는 여전히 중요하다.

하지만 토큰을 줄이는 것이 최종 목적은 아니다. 구현 비용을 아꼈더라도 검증이 모자라 여러 번 다시 작업하거나, 뒤늦게 발견한 결함을 고치는 데 더 큰 비용이 든다면 효율적인 개발이라고 하기 어렵다.

반대로 검증에 비용을 더 쓰더라도 결함을 일찍 찾고 재작업을 줄인다면 전체 비용은 줄어들 수 있다.

그렇다고 검증을 무조건 늘리는 것이 답도 아니다. 검증에는 실행 시간과 인프라 비용이 들고, 잘못된 검사가 내는 오탐도 재작업을 부른다.

그래서 봐야 할 것은 검증에 쓴 토큰의 비율이 아니라, **검증된 작업 하나를 끝내는 데 든 전체 비용**이라고 생각한다. 구현과 테스트에 쓴 모델 비용뿐 아니라 실패한 시도, 재검증, CI, 사람의 개입, 후속 수정 비용까지 들어간다.

![검증을 아낀 경우, 위험도에 맞춰 검증한 경우, 검증을 무조건 늘린 경우의 전체 비용을 막대 길이로 비교한 개념도]({{ '/assets/images/standalone/2026-11-18-trusting-ai-coding-agents/verified-task-cost.svg' | relative_url }})

*개념을 보여 주려고 그린 그림이다. 막대 길이는 실제 측정값이 아니다.*

이건 업계에서 통일해서 쓰는 표준 지표는 아니다. 에이전트 개발의 효율을 따질 때 고려해 볼 만한 관점 정도다.

작업의 위험도와 복잡도에 따라 검증 수준도 달라져야 한다. 문구 한 줄 수정과 결제 로직 변경에 같은 검증 비용을 쓰는 건 맞지 않다.

검증의 목적은 토큰을 많이 쓰는 데 있지 않다. 들인 비용만큼 불확실성을 줄이는 데 있다.

## 6. 실패를 모으는 것과 실패를 규칙으로 만드는 것은 다르다

이 흐름은 내가 [Agent SDD 방법론]({{ '/series/agent-sdd/' | relative_url }})을 설계하면서 고민하던 내용과도 이어진다.

에이전트가 실패할 때마다 새 규칙을 추가하면 시간이 갈수록 지침이 비대해진다. 반대로 실패를 기록하지 않으면 같은 문제가 반복될 때 원인을 추적하거나 개선 효과를 확인하기 어렵다.

그래서 실패를 곧바로 규칙으로 바꾸기보다, 실제로 일어난 문제를 근거와 함께 쌓아 두고 고칠 가치가 있는지 판단하는 과정이 필요하다고 생각한다.

지금 공개해 둔 [Adaptive Agentic SDD](https://github.com/seok-jun/adaptive-agentic-sdd)에도 이 접근을 담으려 하고 있다. 실제 실패 사례를 기록하고, 반복되는 패턴과 위험도, 기대 효과, 적용 비용을 살펴본 뒤 개선할지 판단하는 구조다.

한 번 실패했다고 무조건 규칙을 추가하지 않는다. 그렇다고 피해가 큰 사건을 한 번뿐이었다는 이유로 내버려 두지도 않는다.

![실패를 기록하고 고칠 가치를 판단한 뒤 설계, 검사, 산문 순서로 수단을 고르고 효과를 다시 확인하는 흐름]({{ '/assets/images/standalone/2026-11-18-trusting-ai-coding-agents/failure-to-constraint.svg' | relative_url }})

고치기로 했다면 그다음에는 어떤 방식으로 막을지 정해야 한다. 이때 먼저 보는 것은 기계적으로 판단할 수 있는 조건을 뽑아낼 수 있느냐다.

독립 리뷰에서 검토한 대상과 실제 제출한 대상이 달라지는 문제를 예로 들어 보자.

"항상 같은 코드를 대상으로 리뷰해야 한다"는 지침을 추가할 수도 있다. 하지만 리뷰 대상의 커밋, 경로, 파일 해시, 실제 내용을 비교할 수 있다면 이 문제의 일부는 기계적으로 검증할 수 있다. 지금 방법론에 들어 있는 `review_snapshot.py`가 이런 목적의 검사 도구다.

물론 이 검사를 통과했다고 독립 리뷰의 품질까지 보장되지는 않는다. 리뷰 대상이 같았다는 사실과 리뷰어가 설계 문제를 제대로 찾았다는 사실은 별개다.

기계적 판단도 세 단계로 나눠 볼 필요가 있다.

| 단계 | 하는 일 | 주의할 점 |
| --- | --- | --- |
| 기계적 관측 | 어떤 사건이 일어났는지, 어떤 코드가 바뀌었는지, 검증 결과가 어땠는지 자동으로 모은다 | 모으기만 해서는 판정이 되지 않는다 |
| 기계적 평가 | 모은 증거를 기준으로 문제가 있는지 판정한다 | LLM을 쓰면 판단의 불확실성이 남는다 |
| 결정적 강제 | 명확히 정의한 조건을 어기면 도구나 CI가 작업을 막는다 | 기준 자체가 옳다는 보장은 없다 |

기계적으로 관측할 수 있다고 해서 모두 결정적으로 판단할 수 있는 것은 아니다. 결정적으로 판단할 수 있다고 해서 그 기준이 옳다는 보장도 없다.

그래서 개선의 방향은 전부 자동화하는 쪽이 아니라, 검증할 수 있는 조건을 분명히 가려내고 알맞은 수단을 고르는 쪽이어야 한다.

## 7. 기계적 검증이 모든 문제를 풀어 주지는 않는다

Anthropic도 2026년 1월에 공개한 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)에서 코드 기반 평가, 모델 기반 평가, 사람의 평가를 구분한다. 가능한 영역에서는 재현 가능한 결정적 평가를 쓰고, 의미 해석이 필요한 영역에서는 모델이나 사람의 판단을 쓰는 접근이다. 이 글은 [「감으로는 고칠 수 없다」]({{ '/standalone/2026-10-02-why-ai-agents-need-evals/' | relative_url }})에서 따로 정리한 적이 있다.

현실적인 구분이라고 생각한다.

컴파일이 되는지, 특정 의존성 규칙을 어겼는지는 비교적 분명하게 검사할 수 있다. 반면 사용자의 요구사항을 제대로 이해했는지, 설계가 적절한지, 실제 사용자 경험이 자연스러운지는 여전히 판단의 여지가 크다.

평가 에이전트를 따로 둔다고 이 문제가 저절로 풀리지도 않는다. Anthropic의 [장기 실행 애플리케이션 개발 하네스 연구](https://www.anthropic.com/engineering/harness-design-long-running-apps)에서도 생성자와 평가자를 분리하는 구조를 실험했지만, 평가자의 편향이나 너그러운 판단이 분리만으로 사라지지는 않는다고 설명한다.

더 근본적인 문제는 잘못된 검증 기준이다.

요구사항을 잘못 해석한 채 테스트를 썼다면, 테스트를 아무리 많이 돌려도 잘못된 구현을 정상으로 판단할 수 있다. 형식 검증도 정의한 명세와 가정의 범위 안에서 성질이 성립한다는 것을 증명할 뿐, 명세가 사용자의 의도와 일치한다는 것까지 보장하지는 않는다.

그래서 검증 체계를 강화할수록 무엇을 검증할지 정하는 과정이 더 중요해진다. 자동 검사 결과를 그대로 믿지 말고, 검증 기준 자체를 점검할 수 있어야 한다.

그리고 지금은 기계적 판단이 어렵다고 분류한 문제를 영원히 산문 규칙에 남겨 둘 필요도 없다. 새 테스트 도구가 나오거나 실패 사례가 충분히 쌓여 공통 조건을 뽑아낼 수 있게 되면 다시 평가하면 된다.

방법론이 발전한다는 것은 새 규칙이 늘어나는 일이라기보다, 예전에는 판단하기 어려웠던 문제를 조금씩 더 분명하게 관측하고 검증할 수 있게 되는 과정일지도 모른다.

## 8. 방법론이 줘야 하는 것은 많은 규칙보다 고쳐 나갈 수 있는 구조다

에이전트 개발 환경에서는 모델과 도구가 빠르게 바뀐다. 특정 모델에 맞춰 세밀하게 쓴 지침이 다른 모델에서는 듣지 않을 수 있고, 새 기능이 나오면 기존의 복잡한 우회 절차가 필요 없어지기도 한다.

그래서 공통 방법론이 모든 상황의 해결 방법을 미리 정해 두는 것이 길게 봐서 유리한지 의문이 든다.

나는 꼭 필요한 공통 원칙은 최대한 짧게 유지하고, 프로젝트 특성에 맞춰 검증 환경을 구성할 수 있게 하는 방식이 더 낫다고 생각한다.

이때 방법론이 줘야 하는 것은 규칙 목록이 아니다. 문제가 생겼을 때 원인을 추적하고, 고칠 가치가 있는지 판단하고, 알맞은 제약을 고르고, 결과를 다시 평가하는 과정이다.

그리고 이번 발표를 보고 이 개선 과정에서 하나를 더 눈여겨보게 됐다. **에이전트가 참고하는 코드베이스 자체가 개선 대상**이라는 점이다.

규칙을 추가하고 검사기를 만드는 것만으로는 모자랄 수 있다. 코드에 잘못된 구현이 남아 있으면 에이전트는 그 패턴을 계속 참고한다. 주석이 잘못된 구현을 정당화하고 있으면 그 설명까지 기존 설계 의도처럼 받아들일 수 있다.

그래서 반복되는 문제를 발견했을 때 새 지침이 필요한지만 따지고 끝내면 안 된다. 기존 코드의 구조적인 문제를 고칠 수 있는지, API 설계를 개선할 수 있는지, 잘못된 패턴을 없애거나 막을 수 있는지까지 살펴봐야 한다.

반대로 모든 문제에 새 검사기를 만드는 것도 좋은 방법은 아니다. 검사 도구에도 유지보수 비용이 들고 오탐이 생긴다.

개선은 적용하는 데서 끝나지 않고, 효과를 확인하는 데까지 가야 한다.

내가 설계한 방법론도 이런 개선 순환을 목표로 하고 있지만, 전체 효과를 긴 기간의 실제 프로젝트 데이터로 검증하지는 못했다. 일부 결정적 검사와 제한된 전후 실험은 있다. 장기적으로 결함이 줄었는지, 전체 비용이 나아졌는지는 더 재 봐야 한다. 앞으로 계속 검증해야 할 과제다.

## 9. 결국 기존 소프트웨어 공학으로 돌아가는 걸까?

Lauren Tan의 발표와 Anthropic의 글을 같이 놓고 보면 공통된 방향이 보인다. 에이전트에게 코드를 더 많이 쓰게 하는 것보다, 쓴 코드의 품질을 어떻게 유지하고 검증할지에 관심이 커지고 있다.

하지만 이걸 완전히 새로운 개발 철학이라고 보기는 어렵다. 정적 분석, 자동화 테스트, 명확한 API 설계, 불변 조건, 형식 검증은 모두 소프트웨어 공학에서 오래 다뤄 온 개념이다.

달라진 것은 이런 기법을 쓰는 비용과 필요성이다.

예전에는 검증 도구를 만드는 비용이 커서 적용하지 못했던 영역에도 이제 에이전트를 쓸 수 있다. 동시에 에이전트가 만드는 코드의 양이 빠르게 늘면서 사람의 검토만으로는 신뢰성을 유지하기 어려워졌다.

기존의 공학적 접근을 새 환경에 맞춰 다시 적용하고 있는 셈이다.

이 변화가 업계 전체에 얼마나 퍼졌는지는 아직 조심해서 판단해야 한다. 앞서가는 몇몇 개발자의 경험만으로 일반적인 추세라고 단정할 수는 없다.

그래도 이 흐름은 개발자의 역할을 다시 생각하게 한다.

코드를 직접 쓰는 능력은 여전히 중요하다. 다만 에이전트가 쓴 코드의 품질을 유지하기 위한 환경 설계와 검증 능력의 비중은 점점 커질 수 있다. 프롬프트 작성뿐 아니라 아키텍처 설계, 테스트 전략, 관측 가능성, 실패 분석, 평가 기준 설계까지 여기에 들어간다.

좋은 에이전트 개발 방법론도 이 변화를 담아야 한다. 에이전트에게 어떤 규칙을 전달할지뿐 아니라, 그 규칙을 반복해서 설명하지 않아도 되는 환경을 어떻게 만들지 고민해야 한다.

- 잘못된 구현이 코드베이스에 남아 다음 구현의 기준이 되지 않게 관리한다.
- 반복되는 실패는 충분한 근거를 가지고 고친다.
- 가능한 부분은 기계적으로 검증할 수 있는 제약으로 바꾼다.
- 기계적으로 판단하기 어려운 영역에는 산문과 사람의 판단을 남긴다.

중요한 건 이 경계를 고정하지 않고, 실제 경험과 새 도구를 바탕으로 계속 조정하는 것이다.

발표를 보고 가장 오래 남은 생각은 하나였다.

에이전트를 믿는다는 것은 에이전트가 실수하지 않으리라고 믿는 일이 아니다. 실수가 생겨도 찾아낼 수 있고, 같은 문제가 마구 퍼지지 않으며, 경험을 바탕으로 환경을 계속 고쳐 나갈 수 있다는 확신을 만들어 가는 일에 가깝다.

앞으로 좋은 에이전트 개발 환경을 가르는 기준은 규칙을 얼마나 많이 썼느냐가 아닐 수도 있다. 그 규칙을 다시 설명해야 하는 상황을 얼마나 줄였느냐가 더 중요해질 것 같다.
