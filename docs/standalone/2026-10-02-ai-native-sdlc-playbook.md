# 코드는 더 이상 병목이 아니다 — AI-Native SDLC 쉽게 읽기
{: .no_toc }

_2026.10.02 게시_

![코드는 더 이상 병목이 아니다 — AI-Native SDLC 쉽게 읽기]({{ '/assets/images/standalone/2026-10-02-ai-native-sdlc-playbook/thumbnail.png' | relative_url }})

AI가 코드를 몇 시간 만에 써주는데, 왜 기능 하나가 나가는 데는 여전히 몇 주가 걸릴까.

Anthropic이 2026년 8월 21일에 공개한 [The AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)은 이 질문에서 출발한다. 원문은 코드를 쓰는 단계만 빨라졌고, 그 앞뒤의 기획·리뷰·승인·배포는 여전히 사람 속도로 돌고 있기 때문이라고 본다. 그래서 플레이북은 코드 작성이 아니라 소프트웨어 개발 과정 전체를 AI 기준으로 다시 짜자고 제안한다.

이 글에서는 그 플레이북을 처음 읽는 사람 기준으로 다시 정리해보려 한다. 원문은 실무 예제와 설정 파일이 많아 엔지니어링 리더나 플랫폼 팀을 위한 문서에 가깝다. 여기서는 큰 그림 위주로, 단계별 내용을 표와 도식으로 추렸다. 원문에 없는 해석은 따로 표시했다.

## 먼저 알아둘 용어

본문에 계속 나오는 단어 몇 개만 먼저 정리한다. 다 외울 필요는 없고, 읽다가 막히면 돌아와서 보면 된다.

| 용어 | 한 줄 설명 |
|:---|:---|
| **SDLC** | Software Development Lifecycle. 아이디어가 실제 서비스로 나가기까지의 전 과정. 보통 기획 → 설계 → 구현 → 테스트 → 배포 → 운영 여섯 단계로 본다 |
| **AI-native SDLC** | 그 여섯 단계를 "AI가 각 단계를 수행한다"는 전제로 다시 설계한 것. 원문은 agentic SDLC, AI SDLC도 같은 뜻이라고 밝힌다 |
| **산출물(artifact)** | 각 단계가 끝날 때 남기는 결과 파일. 이 글에서는 `intent.md`, `spec.md`, `plan.md`, 코드와 테스트, PR이 여기에 해당한다 |
| **게이트(gate)** | 다음 단계로 넘어가기 전에 사람이 승인하는 지점 |
| **CLAUDE.md** | 저장소에 두는 안내문. 빌드 명령, 팀 규칙, 자주 하는 실수처럼 신입에게 알려줄 내용을 AI가 세션마다 읽는다 |
| **스킬(skill)** | 조직의 정책·노하우를 AI가 필요할 때 꺼내 쓰도록 폴더로 묶은 것. [Agent Skill 입문]({{ '/standalone/2026-07-24-agent-skill-getting-started/' | relative_url }}) 참고 |
| **훅(hook)** | AI가 어떤 행동을 하기 직전·직후에 자동으로 실행되는 스크립트. 그 행동을 허용하거나 막거나 사람에게 묻는다 |
| **eval** | AI가 일을 제대로 하는지 확인하는 시험 문제 모음. 코드의 테스트처럼 AI 설정의 회귀를 잡는다 |
| **control band** | 운영 지표의 "평소 범위". 이 범위를 벗어나면 이상 신호로 본다 |

## 1. 병목이 옮겨갔다

전통적인 SDLC는 **코드 작성이 가장 비싸고 오래 걸린다**는 전제로 만들어졌다. 그래서 몇 주, 몇 달짜리 개발에 들어가기 전에 요구사항 문서(PRD), 공수 산정, 보안 리뷰 같은 절차로 방향을 단단히 맞춰두었다. 단계마다 담당 역할도 따로 있었다. PM이 요구사항을 쓰고, 아키텍트가 설계하고, 엔지니어가 만들고, QA가 검증하고, 릴리스 팀이 내보내고, 운영 팀이 지켜본다. 단계 사이는 문서·티켓·서명으로 넘어간다.

그런데 Claude Code 같은 에이전트가 코드를 쓰기 시작하면서 이 전제가 깨졌다.

![구현 단계만 줄어들면 앞뒤 단계가 새 병목이 된다]({{ '/assets/images/standalone/2026-10-02-ai-native-sdlc-playbook/bottleneck-shift.svg' | relative_url }})

원문은 구현이 빨라졌을 때 세 가지가 함께 일어난다고 정리한다.

| 일어나는 일 | 왜 문제인가 |
|:---|:---|
| **병목이 구현의 앞뒤로 이동한다** | 기획, 리뷰·테스트, 배포는 여전히 사람 속도다. 구현이 몇 시간으로 줄어도 전체 기간은 크게 줄지 않는다 |
| **통제 장치가 현실과 맞지 않게 된다** | 사람이 쓴 코드를 사람이 한 줄씩 리뷰하는 방식은, 에이전트가 diff 대부분을 쓰는 상황을 따라가지 못한다 |
| **거버넌스 비용이 커진다** | 예외 승인은 여전히 주간·월간 회의를 거친다. 변경이 많아질수록 대기열이 길어진다 |

원문이 드는 예시가 보안 팀이다. 보안 팀의 규모는 사람이 만드는 코드 양에 맞춰져 있다. 에이전트가 코드량을 몇 배로 늘리면 리뷰 대기열이 쌓이거나, 리뷰가 덜 된 코드가 나간다. 규제 산업에서는 둘 다 받아들일 수 없다. 그러니 **보안·정책 검사도 에이전트 속도를 따라가도록 바뀌어야** 한다.

> **참고 · Anthropic 내부 수치.** 함께 읽을 만한 글로 Anthropic 부CISO Jason Clinton이 쓴 [How Anthropic secures its AI-native software development lifecycle](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)(2026.07.21)이 있다. 이 글에 따르면 Anthropic에서는 병합되는 코드의 약 80%를 Claude가 작성하고, 엔지니어 1인당 분기별 코드 출하량은 2021~2025년 대비 평균 8배다. 플레이북의 "구현은 더 이상 병목이 아니다"라는 말이 과장은 아니다.

## 2. 한눈에 보기: 여섯 단계가 하나의 고리가 된다

AI-native SDLC는 단계를 없애지 않는다. 여섯 단계는 그대로 두고, **각 단계 안에서 AI가 일하고 단계 사이를 산출물이 자동으로 이어주는** 구조로 바꾼다. 그리고 마지막 운영 단계에서 발견한 문제가 다시 첫 단계로 들어가면서, 직선이던 흐름이 고리가 된다.

![AI-native SDLC 여섯 단계와 각 단계의 산출물, 판단하는 사람]({{ '/assets/images/standalone/2026-10-02-ai-native-sdlc-playbook/sdlc-loop.svg' | relative_url }})

전통 방식과 나란히 놓으면 차이가 분명해진다. 원문의 비교표를 옮긴 것이다. 원문은 대부분의 조직이 이 두 열 사이 어딘가에 있다고 덧붙인다.

| 단계 | 전통 SDLC | AI-native SDLC |
|:---|:---|:---|
| **기획** Plan | 위원회가 요구사항을 모으고, 워크숍과 서명을 거쳐 사람이 문서로 정리 | Claude가 원천 자료에서 문제를 바로 정리해 `intent.md`로 남긴다. 사람도 읽고 AI도 바로 실행할 수 있는 형식 |
| **설계** Design | 분석가가 명세를 쓰고, 디자이너가 그걸 다시 해석 | 요구사항과 설계를 에이전트와 함께 **한 세션**에서 끝낸다. 회사 기준은 스킬로 담아 git으로 관리 |
| **구현** Build | 테스트와 코드를 사람이 직접 쓰고, 문서는 개발이 끝난 뒤에 작성 | 테스트와 코드를 AI가 생성. 팀의 노하우는 `CLAUDE.md`와 스킬로 버전 관리 |
| **테스트** Test | 단계 경계마다 QA 게이트 | 구현 중에 eval이 계속 돈다 |
| **배포** Deploy | 사람이 모든 코드를 한 줄씩 리뷰. 거버넌스는 리뷰 주기에 따라 들쭉날쭉 | 여러 겹의 AI 리뷰. 사람 리뷰는 규제 대상·핵심 코드에 집중. 훅이 승인 게이트 역할을 하며 AI가 행동하는 순간에 규칙을 강제 |
| **운영** Maintain | 사람이 운영 환경을 지켜보며 버그를 찾음 | 에이전트가 배포된 서비스를 모니터링. 평소 범위를 벗어나면 진단해서 새 `intent.md`로 다시 고리에 넣는다 |

## 3. 산출물의 사슬

플레이북 전체에 걸쳐 반복되는 개념은 커밋된 산출물이다.

각 단계는 결과물을 버전 관리 시스템(git)에 커밋하면서 끝나고, 다음 단계는 그 파일을 읽으면서 시작한다. 초반에는 주로 마크다운 파일이다. 제품 오너와 에이전트가 **같은 파일을 함께 읽고 고칠 수 있기** 때문이다. 구현부터는 코드와 그 기록(테스트, PR, 리뷰 결과)이 산출물이 된다.

| 단계 | 남기는 산출물 | 다음 단계를 시작시키는 것 | 누가 판단하나 |
|:---|:---|:---|:---|
| 기획 | `intent.md` (무엇을, 왜, 어떤 제약 아래) | 제품 오너가 intent를 수락(merge) | 제품 오너 |
| 설계 | `spec.md` (요구사항 + 설계 + 우려 사항 표시) | spec 승인 → plan mode 시작 | 제품 오너. 위험도가 높으면 기술 리드와 상의 |
| 구현 | `plan.md` → 코드와 테스트 | PR 생성 | 엔지니어. 위험도가 높으면 기술 리드·아키텍트 |
| 테스트 | 테스트 결과, 빌드 로그, eval 결과 | 검증 통과 | AI가 먼저 스스로 검증, 이후 코드 오너 |
| 배포 | PR + 리뷰 결과 + 승인 기록 | merge → 파이프라인 | 코드 오너, 운영 배포는 릴리스 매니저 |
| 운영 | 진단 결과, 사고 기록 | 평소 범위 이탈 → 새 `intent.md` | 서비스 오너가 분류(지금 고침 / 일정 잡음 / 기각) |

이 사슬은 그대로 **감사 기록(audit trail)**이 된다. 누가 무엇을 요청했고, 에이전트가 무엇을 만들었고, 누가 승인했는지가 커밋 이력에 남는다. 원문에 따르면 판단이 필요한 모든 결정의 책임은 여전히 사람에게 있고, 바뀌는 것은 사람이 들여다보는 대상이다.

> **기존 도구는 어떻게 하나.** Jira, 요구사항 관리 도구, Figma, 변경 관리 위원회를 이미 쓰고 있다면 한 번에 걷어낼 수 없다. 원문은 산출물마다 **원본(source of truth)을 하나로 정하라**고 권한다. 저장소를 원본으로 삼거나, 기존 시스템을 원본으로 두고 마크다운을 작업 사본으로 쓰거나, 최소한 서로의 ID와 커밋 SHA를 연결해두는 방법이다. 처음에는 연결만 해두는 것부터 시작해도 된다.

## 4. 단계별로 따라가기

원문은 각 단계를 여러 개의 **플레이(play)**로 나눠, 무엇이 바뀌는지 · 어떻게 시작하는지 · 실행 절차 · 거버넌스 · 측정 방법을 같은 틀로 설명한다. 여기서는 원문의 예시 하나를 따라가며 단계별로 본다.

> **예시 시나리오.** 보험사 고객이 "내 보험금 청구가 어디까지 진행됐는지" 물으려고 콜센터에 전화한다. 상담원 통화 시간의 약 3분의 1이 이런 상태 문의에 쓰인다. 고객이 포털에서 직접 진행 상태를 보게 하고 싶다.

### 4-1. 기획: 아이디어를 `intent.md`로

전통 방식에서 아이디어는 백로그, 사용자 스토리, 스토리 포인트, 리파인먼트 회의를 거쳐야 실행된다. 담당자가 바뀔 때마다 원래 의도에서 한 걸음씩 멀어진다.

AI-native 방식에서는 **아이디어를 낸 사람이 직접** Claude와 대화하며 정리한다. Claude가 분석가처럼 범위, 사용자, 제약, 성공 기준을 묻고, 결과를 조직의 템플릿에 맞춰 `intent.md`로 쓴다. 아이디어를 낸 사람이 오해한 부분을 고치고 커밋하면, 제품 오너가 거기서 이어받는다. git을 모르는 사람도 claude.ai나 Cowork에서 GitHub 커넥터로 커밋할 수 있다.

원문 예시를 옮기면 이런 모양이다.

```markdown
# Intent: 보험금 청구 상태 셀프 조회
작성: J. Ortiz (청구 운영팀). 상태: 초안

## 문제
고객이 청구 진행 상황을 물으려고 콜센터에 전화한다.
상담원 통화 시간의 약 3분의 1이 상태 문의에 쓰인다.

## 원하는 결과
고객이 포털에서 청구 상태, 다음 단계, 예상 일자를 본다.

## 영향받는 사용자와 시스템
청구 담당자, 포털 팀, claims-core API

## 제약
포털 세션에 새 개인정보(PII)를 추가하지 않는다. 기존 인증만 사용한다.

## 열린 질문
외부 손해사정사도 접근해야 하나?
```

### 4-2. 설계: 요구사항과 설계를 한 세션에

수락된 `intent.md`를 Claude가 읽고 **요구사항과 설계를 한 번에** 담은 `spec.md`를 만든다. 이때 브랜드, 보안, 컴플라이언스, UX 규칙이 담긴 스킬이 제약 조건으로 적용된다. 정책 위반은 몇 주 뒤 리뷰에서 발견되는 게 아니라, **명세를 쓰는 순간에** 걸러진다.

제품 오너는 명세를 쓰지 않고 **검토한다.** 특히 Claude가 "이 정책 둘은 서로 충돌한다"처럼 표시해둔 우려 사항부터 정책 담당자와 함께 해결한다. 프론트엔드라면 Claude Design으로 목업을 만들어 다듬은 뒤 Claude Code로 넘길 수도 있다.

처음에는 사람이 직접 프롬프트로 실행하고, 익숙해지면 "intent가 merge되면 자동으로 spec 초안 PR이 올라오는" 구조로 바꾼다. 그때부터 제품 오너의 첫 개입은 리뷰가 된다.

### 4-3. 구현: 계획 없이는 코드도 없다

구현 단계에는 플레이가 가장 많다. 표로 먼저 정리하고, 두 가지만 따로 살펴본다.

| 플레이 | 무엇을 하나 | 왜 필요한가 |
|:---|:---|:---|
| **plan mode로 시작** | 코드를 고칠 수 없는 모드에서 Claude가 저장소를 읽고 구현 계획을 쓴다. 엔지니어가 계획을 검토·수정한 뒤 `plan.md`로 커밋 | 방향 수정이 "문서 수정"으로 끝나는 시점에 설계 리뷰를 한다 |
| **auto mode** | 계획이 승인되면 Claude가 편집마다 묻지 않고 구현 | 안전장치가 갖춰지면 사람은 "편집 하나하나"가 아니라 "결과물"을 본다 |
| **CLAUDE.md** | `/init`으로 초안을 만들고 신입에게 필요한 것만 남긴다. 한 페이지 이내 | 사람 머릿속에 있던 팀 지식을 AI가 매 세션 읽는 파일로 만든다 |
| **스킬** | 일관되게 지켜져야 하는 정책을 `SKILL.md`로 작성. 정책이 바뀌면 정책 담당자가 변경을 승인 | 정책을 "알아서 지켜주길" 바라는 대신 작업 중에 적용한다 |
| **훅 (가드레일)** | 보호된 경로 편집 차단, 편집 후 포매터·린터 실행, 비밀값이 diff에 섞이지 않게 막기 | 반드시 지켜야 하는 규칙을 결정론적으로 강제한다 |
| **병렬 세션·서브에이전트** | worktree마다 별도 Claude 세션을 띄우고, 반복 작업은 서브에이전트로 분리 | 엔지니어 한 명이 여러 작업을 동시에 진행한다 |

**하나. 계획을 먼저 커밋한다.** 원문 기준으로 좋은 계획의 조건은 "대화를 한 번도 본 적 없는 엔지니어가 계획만 보고 구현할 수 있을 것"이다. 바뀌는 파일, 작업 순서, 위험 요소, 무엇으로 완성을 증명할지가 들어간다. 구현이 계획과 달라지면 같은 커밋에서 `plan.md`도 고친다. 나중에 PR 리뷰가 diff를 이 계획과 대조한다.

```markdown
# Plan: 보험금 청구 상태 셀프 조회 (intent.md 2026-06-02 기준)
## 바뀌는 파일
portal/src/claims/StatusPanel.tsx (신규), claims-api/routes/status.py,
claims-api/tests/test_status.py
## 작업 순서
1. 기존 인증 뒤에 상태 조회 엔드포인트 추가
2. 엔드포인트를 쓰는 패널 구현
3. 포털 메뉴에 연결
## 위험
claims-core API는 초당 50건으로 제한된다. 패널은 캐시해야 한다.
## 증명
test_status.py가 청구 상태 네 가지를 모두 다룬다. 스크린샷이 승인된 목업과 일치한다.
```

**둘. 스킬은 권고, 훅은 강제다.** 이 구분이 플레이북 전체에서 반복된다.

| | CLAUDE.md | 스킬 | 훅 |
|:---|:---|:---|:---|
| 성격 | 상시 안내문 | 필요할 때 꺼내 쓰는 지침 | 실행되는 스크립트 |
| 강제력 | 권고 | 권고 (AI가 따를 가능성을 높임) | 강제 (허용·차단·사람에게 묻기) |
| 어울리는 내용 | 빌드 명령, 팀 규칙, AI가 자주 틀리는 것 | 보안 표준, API 설계 규칙, 브랜드 규칙처럼 일관되게 적용돼야 하는 정책 | 절대 어기면 안 되는 규칙 |
| 원문의 한 줄 | "Claude가 같은 실수를 두 번 하면 그 교정은 CLAUDE.md로" | "스킬은 위반을 드물게 만든다" | "훅은 위반을 거의 불가능하게 만든다" |

### 4-4. 테스트: 사람이 보기 전에 AI가 먼저 확인한다

전통 방식에서는 "이 코드가 동작한다"는 신호가 늦게 온다. CI는 몇 분 뒤, 테스터는 며칠 뒤, 운영 환경은 몇 주 뒤다. 에이전트가 코드를 쓰는데 신호가 늦으면, 사람이 그 결과물을 전부 확인해야 하고 그 사람이 병목이 된다.

그래서 원문의 첫 번째 원칙은 **"Claude에게 스스로 검증할 수단을 줘라"**다.

| 할 일 | 구체적으로 |
|:---|:---|
| 검증을 명령 하나로 | 여러 단계 확인 작업을 `make test`처럼 실패 시 0이 아닌 값을 돌려주는 명령 하나로 묶는다 |
| 목표를 숫자로 | "test_status.py의 테스트가 모두 통과", "엔드포인트가 새 필드와 함께 200 응답"처럼 AI가 사람에게 묻지 않고 확인할 수 있게 쓴다 |
| 버그는 실패하는 테스트부터 | 버그를 재현하는 테스트를 먼저 커밋하고, **테스트는 고치지 말고** 코드만 고쳐 통과시키게 한다 |
| UI는 눈으로 | 브라우저·스크린샷 도구를 주고 목업과 비교하며 두세 번 반복하게 한다 |
| 검증 장치 보호 | 수정 작업 중에는 훅으로 테스트 파일 편집을 막는다. 코드를 고치는 쪽이 검사 기준을 약하게 만들 수 없어야 한다 |

또 하나는 **eval을 CI에 넣는 것**이다. 최근 실제 작업 20~50개를 골라 "프롬프트 + 합격 기준"으로 만들어두고, `CLAUDE.md`·스킬·훅이 바뀔 때마다 돌린다. AI를 움직이는 설정도 코드처럼 회귀 테스트를 받아야 한다는 뜻이다. 운영 사고가 나면 그 사고도 eval로 추가해 다시는 같은 문제가 통과하지 못하게 한다.

### 4-5. 배포: AI는 운영 게이트 직전까지만

원문은 이 단계의 원칙을 이렇게 적는다. **에이전트는 운영 게이트까지 모든 일을 하고, 그 너머로는 아무것도 하지 않는다.**

**AI가 PR 리뷰를 주고받는다.** 모든 PR이 같은 리뷰 과정을 거친다. 기술 리드가 저장소 루트에 `REVIEW.md`로 리뷰 기준(버그, 보안, `spec.md`·`plan.md` 준수 여부)과 "중요(Important)"와 "사소함(Nit)"의 기준을 적어둔다. 리뷰어가 `@claude`를 태그하면 Claude가 지적 사항을 고쳐 푸시한다. 같은 실수가 리뷰에서 두 번 지적되면 그 교정은 `CLAUDE.md`로 들어간다. 그리고 **코드를 쓴 에이전트는 그 코드를 승인할 수 없다.** 승인은 브랜치 보호 규칙을 통해 사람이 한다.

**훅이 승인 게이트가 된다.** 변경 관리 승인, 릴리스 승인처럼 반드시 남아야 하는 사람의 승인을 목록으로 만들고, 각각을 훅으로 표현한다. 팀 훅은 저장소의 `.claude/settings.json`에, 절대 꺼지면 안 되는 훅은 플랫폼 팀이 관리하는 managed settings에 둔다. 엔지니어 개인이 끌 수 없다.

**환경마다 자율성을 다르게 준다.**

| 환경 | AI가 할 수 있는 일 | 사람의 역할 |
|:---|:---|:---|
| 개발 | 자유롭게 배포 | 결과 확인 |
| 스테이징 | 개발과 운영의 중간 | 조직이 정함 |
| 운영 | 릴리스를 **준비**까지만 | 릴리스 매니저가 승인. 훅이 이 게이트를 강제 |

파이프라인에서는 실패한 빌드 원인 분석, 불안정한 테스트 요약, 변경 내역 초안처럼 **읽기만 하는 판단 작업**부터 AI에게 맡긴다. 쓰기 작업은 기존 게이트 뒤에 붙인다. AI가 만든 모든 변경은 PR로 들어오고, main에 직접 푸시할 길은 없다. 롤백은 파이프라인에서 가장 많이 연습된 경로여야 한다. 다음 단계에서 AI가 직접 부를 수 있기 때문이다.

### 4-6. 운영: 고리가 닫힌다

앞의 다섯 단계는 모두 사람이 시작 버튼을 누른다. 운영 단계는 다르다. **사람이 호출하지 않아도** 트리거가 Claude를 부른다. 지표 이탈, 새 티켓, 채널 메시지, 정해진 일정이 트리거가 된다.

![지표 이탈 정도에 따라 AI가 할 수 있는 일이 달라진다]({{ '/assets/images/standalone/2026-10-02-ai-native-sdlc-playbook/control-bands.svg' | relative_url }})

이 단계에서는 두 가지를 지킨다.

- **감지는 AI가 하지 않는다.** 최근 30일 평균과 표준편차로 평소 범위를 잡는 결정론적 스크립트가 감지한다. 스크립트도 버전 관리하고 단위 테스트한다.
- **AI의 권한은 이탈 정도에 따라 단계적으로 열린다.** 1σ에서는 기록만, 2σ에서는 읽기 전용 진단, 3σ에서도 PR을 열거나 미리 승인된 런북을 실행하는 데까지만이다. 이 단계 기준도 `bands.yaml` 같은 설정 파일로 버전 관리한다.

AI가 찾은 내용은 기획 단계 형식의 `intent.md`로 작성되어, 다른 아이디어와 똑같이 리뷰 게이트를 거친다. 서비스 오너는 이 대기열을 보고 "지금 고침 / 일정 잡음 / 기각"을 정한다. 수정이 배포되면 그 사고는 eval로 추가된다. **사람은 일을 시작하는 역할에서 분류하고 검토하는 역할로** 옮겨간다.

원문은 같은 원리를 두 군데 더 적용한다.

| 플레이 | 내용 |
|:---|:---|
| **정기 보안 스캔** | 보안 스캔은 "특정 시점, 특정 모델" 기준의 결과라 금방 낡는다. 일정에 따라 다시 돌리고, PR 하나로 끝나는 수정은 리뷰 게이트로, 더 큰 문제는 `intent.md`로 보낸다. 원문은 Claude Security를 예로 든다 |
| **Claude Tag로 온콜** | Slack 채널에 Claude가 자기 계정으로 참여해 사고의 첫 대응자가 된다. 대화, 진단, 사람의 승인, 수정이 모두 채널에 남아 그대로 감사 기록이 된다 |

---

## 5. 그래서 사람은 어디에 남나

여기까지 보면 AI가 다 하면 사람은 뭘 하느냐는 질문이 나올 수 있다. 원문은 역할이 사라지는 게 아니라 들여다보는 대상이 바뀐다고 답한다. 아래 표는 원문의 단계별 설명에서 각 역할에 해당하는 부분을 모은 것이다.

| 역할 | 전에는 | 이제는 |
|:---|:---|:---|
| 아이디어를 낸 사람 | 제품 팀을 설득해 대신 문서를 써달라고 부탁 | Claude와 직접 `intent.md`를 쓰고 커밋 |
| 제품 오너 | 요구사항 문서를 직접 작성 | `intent.md` 수락 여부를 판단하고, AI가 쓴 `spec.md`를 검토 |
| 정책 담당자 (보안·컴플라이언스 등) | 몇 주 뒤 리뷰에서 위반을 발견 | 정책을 스킬로 만들고, 스킬 변경을 승인하고, AI가 표시한 우려 사항에 답한다 |
| 엔지니어 | 설계를 읽고 직접 코드 작성 | 계획을 검토·승인하고, 여러 세션을 지휘하고, 결과물을 리뷰 |
| 기술 리드 | 모든 PR을 직접 리뷰 | `REVIEW.md`로 리뷰 기준을 정하고, 매달 리뷰 결과를 평가해 조정 |
| 플랫폼 팀 | 빌드·배포 스크립트 관리 | 훅, managed settings, eval, 샌드박스처럼 AI가 일하는 **울타리**를 관리 |
| 릴리스 매니저 | 배포 절차를 직접 수행 | AI가 준비한 릴리스를 승인 |
| 서비스 오너·온콜 | 경보를 받고 직접 원인 분석 | AI가 진단해 올린 `intent.md`를 분류 |

원문은 이 문장으로 끝난다. **"The loop keeps running. Human judgement stays above it."** 고리는 계속 돌고, 사람의 판단은 그 위에 있다.

## 6. 어디서부터 시작하나

원문은 이 모든 걸 한 번에 하라고 하지 않는다. 플레이마다 **선행 조건**을 적어두었고, 선행 조건이 없는 플레이부터 시작하라고 한다. 그 관계를 세 묶음으로 정리하면 다음과 같다.

![선행 조건이 없는 플레이부터 시작해 게이트가 필요한 자동화로 넓혀간다]({{ '/assets/images/standalone/2026-10-02-ai-native-sdlc-playbook/adoption-order.svg' | relative_url }})

자동화 순서에 대해서는 원문 전체에서 같은 말을 한다. 게이트가 자동화보다 먼저 있어야 한다. CI/CD에 AI를 넣기 전에 PR 리뷰와 훅 게이트가 있어야 하고, 운영을 자동으로 돌리기 전에 롤백 경로가 검증되어 있어야 한다. 게이트 없이 자동화부터 붙이면, 빨라지는 건 사고도 마찬가지다.

### 잘 되고 있는지는 어떻게 아나

원문은 모든 플레이에 **선행 지표**(빨리 움직이는 신호)와 **후행 지표**(결과로 드러나는 신호)를 붙여두었다. 대부분 git 이력, PR 메타데이터, CI 로그처럼 이미 쌓이고 있는 데이터에서 읽을 수 있는 것들이다. 대표적인 것만 추리면 다음과 같다.

| 단계 | 선행 지표 | 후행 지표 |
|:---|:---|:---|
| 기획 | 첫 대화부터 `intent.md` 커밋까지 걸린 시간 (몇 주 → 몇 시간 기대) | 제품 오너가 수락한 intent 비율 |
| 설계 | `intent.md` 커밋부터 `spec.md` 커밋까지 걸린 시간 | 구현 시작 후 요구사항이 다시 바뀐 횟수 |
| 구현 | 첫 구현 그대로 merge된 비율 | 변경당 재작업 횟수, merge된 diff가 `plan.md`와 일치하는 정도 |
| 테스트 | AI가 쓴 변경의 CI 첫 통과율 | PR당 리뷰 시간, 변경 실패율 |
| 배포 | 첫 리뷰까지 걸린 시간 (몇 분 기대) | merge 전에 잡힌 결함 대 운영에서 새어 나간 결함 |
| 운영 | 지표 이탈부터 `intent.md`가 분류 대기열에 오르기까지 시간 | 같은 종류 사고의 재발 횟수 |

이 지표들이 보려는 것은 사람의 주의가 "각 단계를 시작하는 일"에서 "AI가 판단을 요청한 지점을 검토하는 일"로 옮겨갔는지다.

## 7. 읽으며 짚어둘 점

여기부터는 원문 내용이 아니라 내 해석이다.

**벤더가 쓴 실행 가이드다.** 이 문서는 Anthropic Applied AI 팀이 고객과 일하며 정리한 모범 사례이고, 효과를 독립적으로 측정한 연구는 아니다. 등장하는 도구도 대부분 Claude 제품군이다. 다만 뼈대가 되는 원칙(산출물 커밋, 권고와 강제의 분리, 게이트 먼저, 단계적 권한)은 특정 도구에 묶이지 않는다.

**스킬과 훅의 구분이 가장 실용적이다.** 이 블로그의 [에이전트 도구사 3년]({{ '/standalone/2026-07-28-agent-scaffolding-history/' | relative_url }})에서 모델에 흡수되지 않고 끝까지 남는 층으로 검증을 꼽았는데, 플레이북도 같은 자리에 결정론적 장치를 둔다. 감지는 스크립트가, 강제는 훅이, 승인은 사람이 한다. AI에게 맡기는 건 그 사이의 판단 작업이다.

**`intent → spec → plan` 흐름은 낯설지 않다.** [Agent SDD 실무 개발]({{ '/series/agent-sdd/' | relative_url }}) 시리즈에서 다룬 "구현 전에 짧은 명세를 쓰고, 그 명세를 기준으로 검증한다"는 방식과 같은 방향이다. 플레이북은 이를 개인 작업 습관에서 조직 전체의 파이프라인으로 넓힌 것에 가깝다.

**이해하지 못하는 승인은 여전히 위험하다.** 사람이 "게이트에서 판단한다"는 구조는 사람이 판단할 수 있을 때만 의미가 있다. 리뷰할 양이 줄어든 대신 한 번의 승인이 무거워진다. 이 문제는 [이해하지 못하는 결정을 승인한다는 것]({{ '/standalone/2026-07-21-human-ai-judgment/' | relative_url }})에서 따로 다뤘다.

## 정리

- AI가 코드를 빠르게 쓰면서 병목은 구현의 **앞뒤**(기획, 리뷰·테스트, 배포)로 옮겨갔다.
- AI-native SDLC는 단계를 없애지 않는다. 각 단계에서 AI가 일하고, **커밋된 산출물**이 단계 사이를 잇고, 운영에서 찾은 문제가 다시 기획으로 돌아가는 **고리**를 만든다.
- 산출물의 사슬(`intent.md` → `spec.md` → `plan.md` → 코드·테스트 → PR → 새 `intent.md`)이 그대로 감사 기록이 된다.
- 스킬은 권고, 훅은 강제다. 반드시 지켜야 하는 규칙에는 결정론적 장치를 둔다.
- AI는 운영 게이트 직전까지만 일한다. 승인과 책임은 사람에게 남는다.
- 선행 조건이 없는 것부터 시작하고, 게이트를 자동화보다 먼저 만든다.
